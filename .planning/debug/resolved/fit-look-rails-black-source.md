## Resolution

root_cause: RunStylePostFit's GPU readback pairs a TextureFormat.RGBA32 request (4 bytes/pixel buffer) with GetData<Color>() (16 bytes/element) — NamerEditorWindow.cs:2483-2493. GetData<T> views the raw readback buffer as sizeof(T) elements, so the fit consumes w*h/4 "pixels" whose channels are four real texels' (r,g,b,255) byte-quads bit-reinterpreted as ~-1.8e38 finite floats. IsFinitePixel passes them; NamerStylePostMath.TonemapLdr crushes them to 0; every estimator rails together deterministically (EV log2(ref/~0) -> +10 clamp; srcSpread~0 -> contrast +100; srcChroma~0 -> saturation +100; Fsrc mass in bin 0 -> staircase curves), producing the white Stylized+Post render via exp2(10). The fit path is the ONLY RGBA32+GetData<Color> mix in the codebase (project convention: RGBA32 pairs Color32; RGBAFloat pairs Color — NamerDecompPipeline:663/671, NamerRoughnessPipeline:259/351/399).
fix: (1) NamerEditorWindow.cs RunStylePostFit readback requests TextureFormat.RGBAFloat (matches GetData<Color>'s 16-byte element layout, AccumulateSource's HDR-linear domain, and the project float-RT convention) — one-line change plus explanatory comment. (2) NAMERStylize.compute NamerStylizeHue + NamerStylizeHsvUnit restructured to single-return with locals initialized at declaration (behavior-identical; silences the two Metal 'potentially uninitialized variable' Info warnings). (3) New regression test NamerStylePostFitReadbackTests pinning the seam contract: one Color per texel, means match an independent RGBA32+Color32 byte oracle of the same target, and a healthy-source identity fit does not rail any knob.
