# Phase 03.1: AO Extraction — Un-multiply Baked AO + Geometry Bake — Research

**Researched:** 2026-08-28
**Domain:** Ambient-occlusion extraction from base color (image-space) + mesh-visibility AO bake (geometry) feeding the existing NAMER GPU pack pipeline
**Confidence:** MEDIUM-HIGH (stack + round-trip invariant HIGH; image-space extraction MEDIUM; geometry-bake route MEDIUM with one HIGH-risk hand-rolled component)

## Summary

Phase 03.1 delivers real ambient occlusion to two consumers that today receive a dead white fill when no authored `_OcclusionMap` exists: the `CSNormalize` un-multiply divisor and the packed surface B channel. Two AO sources land in one phase (user override of the defer recommendation): (1) **image-space extraction** — a GPU-compute low-frequency luminance decomposition of the base color, which fixes the urgent "always-white AO, dead `_AoUnmultiplyStrength` slider" live pain; and (2) **geometry bake** — a per-texel multi-directional visibility test from mesh geometry (high-res occluder over the selected mesh), replicating the Blender Cycles reference without Cycles.

Both sources converge on a single AO texture (green channel, linear) that becomes `_AoIn` in the existing kernels. The SAME AO value is the un-multiply divisor and the B channel, so `base_unmul × ao_packed ≈ base` holds by construction (D-08). The un-multiply divisor floor is raised from `NAMER_EPSILON` to `0.1` — but only for extracted/baked AO, so authored-map behavior stays byte-identical (D-07/D-09). Three new controls (AO blur radius, AO strength, AO contrast) shape the AO output source-agnostically (D-11), debounced in the existing window (D-13), persisted via `NamerProcessorSettings` (D-03).

**Primary recommendation:** Ship image-space extraction as pure compute shaders in a new `Compute/NAMERAO.compute`, run automatically when `_OcclusionMap` is absent (fast, fits the 300 ms debounce). Ship the geometry bake as a **CPU Burst raycast** (Unity.Mathematics + Collections, hand-rolled Möller–Trumbore + a BVH) with the result uploaded as a texture through the existing raw-copy path — NOT part of the debounced recompute (it is a cached, explicit, reduced-resolution operation). Do not use GPU depth-projection (hard to test headless, non-deterministic, poorly maps to the reference cage-offset/ray-distance defaults).

### Pattern 1: Separable Gaussian Blur (image-space low-pass)
**What:** A gaussian low-pass is applied in two passes — horizontal then vertical — each reading only `2×radius+1` neighbors, so cost is O(radius) not O(radius²).
**When to use:** The image-space extraction's low-frequency decomposition (large radius) and the user-facing AO blur tweak (D-11).
**Key detail:** Do not use `groupshared`/apron tiling — a simple `[numthreads(8,8,1)]` kernel reading neighbors directly from the source texture is correct, simpler, and avoids the Metal/D3D11 groupshared budget (16–32 KB) entirely. Radius is a named constant/uniform.
```hlsl
// Source: standard separable-gaussian pattern (textbook; applied in compute form)
[numthreads(8,8,1)]
void CSBlurH(uint3 id : SV_DispatchThreadID)
{
    if (id.x >= _Size.x || id.y >= _Size.y) return;
    float acc = 0.0; float wsum = 0.0;
    for (int x = -_Radius; x <= _Radius; ++x)
    {
        float w = exp(-(float)(x*x) / (2.0 * _Sigma * _Sigma));
        acc += _Src[int2(clamp(id.x + x, 0, (int)_Size.x - 1), id.y)].r * w;
        wsum += w;
    }
    _Dst[id.xy] = acc / wsum;
}
// CSBlurV is the transpose; dispatch H then V into a ping-pong RT pair.
```

### Pattern 2: Image-space AO = divide by blurred luminance
**What:** AO estimate = normalized low-frequency luminance of the base color. Un-multiply is `base / max(ao, floor)`. This is the classic "de-light / de-bake" technique (Substance "Delight", Houdini Labs Delight, photogrammetry de-lighting).
**When to use:** When `_OcclusionMap` is absent (D-07 auto path). Blur-before-divide is mandatory; divide-before-blur smears high-frequency albedo into the shading estimate and produces halos.
**Luminance:** compute in linear space (apply `SRGBToLinear` first if `_SourceIsSrgb`, matching `CSNormalize`), e.g. `luma = dot(base, float3(0.2126, 0.7152, 0.0722))`.
```hlsl
// Estimation kernel (linear space). _BaseLinear is the sRGB-decoded base (reuse CSNormalize's decode).
float ao = saturate(luma / max(_LumaAverage, 1e-4)); // normalize low-frequency signal
ao = max(ao, _AoFloor);                              // 0.1 floor caps un-multiply darkening
```

### Pattern 3: Burst per-texel visibility (geometry bake)
**What:** For each UV-covered texel, reconstruct the world position + normal via barycentric UV interpolation, offset outward by the cage offset (`0.01`) along the normal, cast a fixed 64-direction set (e.g., cosine-weighted hemisphere around the normal, or a Fibonacci sphere), and test against a BVH over the occluder triangles. AO = unoccluded / 64.
**When to use:** The geometry bake (Wave 2). This is the highest algorithmic risk; it must be Burst-compiled and BVH-accelerated.
**Determinism/testability rationale (why Burst over GPU depth-projection):** a fixed direction table + fixed float math is reproducible and runnable in the headless EditMode clone runner (`/tmp/namer-gsd/run-tests-in-clone.sh EditMode 25`, no scene render). A depth-projection bake needs a live camera render and rasterization, which is non-deterministic and untestable headless.
```csharp
// Source: Möller–Trumbore (Wikipedia / Scratchapixel); re-expressed in Unity.Mathematics. ~20 lines.
[BurstCompile]
struct RayTriangleJob : IJobParallelFor
{
    [ReadOnly] public NativeArray<float3> Vertices;
    [ReadOnly] public NativeArray<int3>  Triangles;

    [ReadOnly] public NativeArray<float3> RayDirs;

```

### Pattern 4: UV-seam dilation via Jump Flood
**What:** After the bake, dilate AO across UV-island boundaries by 16 px (reference `margin`). Seed island-edge texels as JFA seeds, run `log2(maxDimension)` jump-flood passes propagating the nearest valid seed's AO.
**When to use:** Geometry-bake output only (the image-space path needs no seam dilation — it already covers the full texture). The 16 px margin prevents seam darkening under bilinear/mip sampling.

### Anti-Patterns to Avoid
- **Writing AO into the red/alpha channel:** `CSNormalize`/`CSOctahedralEncode` read `_AoIn[id.xy].g`. The extracted/baked AO must be written to the **green** channel (or grayscale).
- **Floating the divisor unconditionally:** raising the floor to 0.1 for authored maps breaks the D-07 "byte-identical today" guarantee. The floor must be conditional (authored → `NAMER_EPSILON`, extracted/baked → `0.1`).
- **Blur-after-divide ordering:** produces halos and smears albedo into the shading estimate. Always blur the luminance first, then divide.
- **Ray origin on the surface (no cage offset):** rays starting exactly on the mesh immediately self-intersect, producing black AO. The `0.01` outward normal offset (reference `cage_extrusion`) is load-bearing — do not drop it (user explicitly requested it be preserved).
- **Brute-force O(n) ray traversal:** 268 M rays × all-triangles is infeasible; a BVH (or spatial grid) is mandatory.
- **Putting the bake on the 300 ms debounce:** a 2048² × 64-ray Burst bake is seconds-scale; keep it cached/explicit, not in the debounced recompute.

## Common Pitfalls

### Pitfall 1: The AO green-channel contract
**What goes wrong:** A new AO texture written with AO in R (or grayscale-into-R only) makes `_AoIn.g` read ~0, producing the black-AO/oversaturated-base double symptom already fixed in Phase 2's white-fill regression test.
**Why it happens:** `CSNormalize` and `CSOctahedralEncode` read `_AoIn[id.xy].g` (Unity's `_OcclusionMap` convention stores AO in G).
**How to avoid:** Write AO into G (or grayscale so G=R=B). Add a golden test asserting a known AO value survives to B and to the divisor.
**Warning signs:** AO debug view black, base view saturated, B channel ~0 while the extraction texture visually shows AO in R.

### Pitfall 2: sRGB/linear on the AO intermediate
**What goes wrong:** Declaring the AO intermediate sRGB (or writing sRGB-encoded AO) makes the divisor wrong and double-converts.
**How to avoid:** The AO intermediate is `R8G8B8A8_UNorm` **linear** (match the existing `aoIn` descriptor); sRGB decode of the base happens only once, in the extraction kernel (mirroring `CSNormalize`'s `_SourceIsSrgb` gate). Reuse the `Upload`/`NamerRawCopy` contract.

### Pitfall 3: Breaking the round-trip invariant by flooring B
**What goes wrong:** Flooring the stored B channel at 0.1 (instead of only the divisor) makes deep-cavity AO return 0.1 in B while the divisor is also 0.1 — the round-trip then darkens `base × (ao/0.1)` in cavities, i.e. "double-darkening" reappears.
**How to avoid:** B stores the raw tweaked AO (`_AoIn.g`, unchanged); only `CSNormalize`'s divisor is floored. This matches the reference (`remove_ao_from_texture` clips only the divisor; the material keeps the raw baked AO map).

### Pitfall 4: Self-intersection when the occluder is the selected mesh (D-03 default)
**What goes wrong:** With no high-res override, ray origins lie on the same surface they test against; without the cage offset, every ray reports "occluded" at t≈0.
**How to avoid:** Offset the origin outward along the interpolated normal by `0.01` (reference `cage_extrusion`), and begin traversal at `t_min > epsilon`. A test with a flat plane should yield AO ≈ 1.0.

### Pitfall 5: Performance cliff at full resolution
**What goes wrong:** Baking at 2048² × 64 rays (≈ 268 M rays, × ~20–50 triangle tests each through the BVH) is seconds-to-tens-of-seconds in Burst, stalling the interactive preview.
**How to avoid:** Bake at a reduced resolution (e.g., 512²–1024², capped at the base-map size), then GPU-bilinear-upsample + 16 px dilate to base resolution. AO is low-frequency; upsampling is visually lossless. Keep the bake cached and explicit, off the 300 ms debounce.

### Pitfall 6: Naming collision — "AO strength" vs `_OcclusionStrength`
**What goes wrong:** The new processing-time "AO strength" control (D-11) is distinct from the runtime `_OcclusionStrength` metadata (`ao = surface.b * _OcclusionStrength`). Confusing them double-applies strength or breaks the decode.
**How to avoid:** Name the new control distinctly (e.g., `AoStrength` processing control in `NamerProcessorSettings`, applied to the AO texture) and keep `_OcclusionStrength` untouched. Document the distinction in `NamerSourceModel`.

### Möller–Trumbore in Unity.Mathematics (Burst)
```csharp
// Source: Möller–Trumbore (Wikipedia, 1997); re-expressed with Unity.Mathematics.
static bool RayTriangle(float3 origin, float3 dir, float3 v0, float3 v1, float3 v2,
                        out float t)
{
    const float kEps = 1e-8f;
    float3 e1 = v1 - v0, e2 = v2 - v0;
    float3 p = math.cross(dir, e2);
    float det = math.dot(e1, p);
    if (math.abs(det) < kEps) { t = 0; return false; }
    float inv = 1f / det;
    float3 s = origin - v0;
    float u = math.dot(s, p) * inv;
    if (u < 0f || u > 1f) { t = 0; return false; }
    float3 q = math.cross(s, e1);
    float v = math.dot(dir, q) * inv;
    if (v < 0f || u + v > 1f) { t = 0; return false; }
    t = math.dot(e2, q) * inv;
    return t >= kEps;                       // t_min > eps: ignore the origin surface itself
}
```

## Open Questions

1. **Is the geometry bake automatic or explicit?**
   - What we know: D-07 says extraction/bake "runs automatically only when the map is absent"; D-03/D-04 imply a high-res mesh field (an explicit interaction); D-02 sequences extraction first, bake second; D-13 says all *controls* are debounced.
   - What's unclear: whether the bake fires on every recompute (too slow per A1) or is a separate cached/explicit "Bake AO" action.
   - Recommendation: extraction is the automatic default (debounced); the bake is an explicit, cached action (with the high-res override field) whose result replaces extraction in the preview. Surfacing this to the user for confirmation before execution is advisable.

2. **Bake resolution + direction-count policy for preview vs final.**
   - What we know: reference = 64 samples at max(2048, main size); our Burst route is CPU-bound (A1).
   - What's unclear: exact preview resolution cap and whether to use fewer directions for preview.
   - Recommendation: preview 512² / 32 directions; final 1024² / 64 directions; upsample + dilate to base size. Planner should treat these as defaults to be tuned against a real high-poly asset.

3. **Relationship between the extraction's internal low-pass radius and the D-11 blur radius.**
   - What we know: extraction needs a large low-pass; D-11 blur applies to both sources.
   - Recommendation: keep them distinct (internal auto-derived low-pass + user-facing blur tweak), as assumed in A5.
