# Phase 04.1: Baked-response roughness extraction + zero-residual one-texture mode - Context

**Gathered:** 2026-09-06
**Status:** Ready for planning

<domain>
## Phase Boundary

Assets whose base texture has material response (gloss/shading/cavity) baked in — and no dedicated roughness map (Neo is the motivating case) — get that baked response extracted into the **6-bit roughness bits (A 0–5)** of the packed surface texture. The cleaned base is then refit into vertex colors, the residual collapses, and the Phase-4 **D-13 auto-drop becomes the primary path**: *material = one RGBA8 surface PNG + a vertex-colored mesh* — no base texture bound, no residual file. The residual-texture fallback stays for assets whose base contains genuine albedo detail (decals, fabric weave, freckles) that survives extraction.

**Locked direction (from the exploration session — see canonical refs, not re-decided here):**
- **Format semantics do not change.** Bits 0–5 keep meaning "roughness"; only the *source* of the values changes. Golden-vector decode equivalence and `NamerSurface.hlsl` decode are untouched.
- Blur is the frequency separator: blurred base ≈ what vertex-color interpolation can hold; sharp-minus-blur remainder is the extraction candidate.
- Honest gate: "no residual texture" is earned per-asset by the fit (extract → refit → drop residual when within threshold, else fallback) — D-13 extended, never assumed.
- Neo is the acceptance case: processes to one texture, renders correctly, no residual file.

**Out of boundary:** metallic extraction from base (Blender has `extract_metallic`; not requested), stylization interplay incl. roughness simplification (Phase 5, STYL-06), bake-to-generation AO wiring (W1 accepted divergence stands), batch processing (v2 BATCH-01), packed-format versioning changes.

</domain>

<decisions>
## Implementation Decisions

### Extraction gate
- **D-01:** Roughness extraction runs **automatically when the source has no authored roughness/smoothness map** — the 03.1 D-07 authored-wins pattern: an authored map always wins and its path stays byte-identical to today; extraction is the scalar-only/no-map path (Neo's case). Extraction never overrides authored data.
- **D-02:** The user gets a **strength override** control for the extraction — window control, EditorPrefs-persisted via `NamerProcessorSettings`, debounced live recompute (Phase-03 D-10 / Phase-4 D-15 pattern). Strength 0 = off.

### Estimator
- **D-03:** **Both estimator routes ship, as a selectable option:** Blender-parity Sobel (edge-magnitude on luminance, matching `namer_core.py` `extract_roughness`) **and** fit-driven (extraction strength calculated to minimize the post-refit residual — the adaptive-resolution-ladder philosophy). *Assumption to confirm at plan review: default = fit-driven* (the exploration notes' direction: "the Unity version should *calculate* how much to extract"); Sobel mode exists for Blender parity.
- **D-04:** The fit-driven pass follows the **`NamerAOBaker` pattern** (user-referenced): deterministic CPU Burst (`IJobParallelFor`, fixed tables, never `System.Random`), cancellable progress with injectable headless `shouldCancel`, an explicit one-time action **off the 300 ms debounce**, pipeline-level caching (`HasCachedBake`/`RequestBake` precedent), caller-owned result buffers. Per-pixel texture math stays GPU compute (NORM-03).

### Fallback residual
- **D-05:** When the residual fallback triggers on an extraction-processed asset, the refit/residual is fit against the **cleaned (post-extraction) base** — extraction is never undone on the fallback path; the extracted roughness stays in bits 0–5.

### Escape hatch (roughness-offset input)
- **D-06:** The optional **single RGBA shader input to offset roughness ships in 04.1** — the fallback for per-texel detail that 6-bit extraction underfits. It is a material-level optional input, **not** a packed-format change: neutral-when-unset so decode equivalence and the one-texture happy path are untouched (unset input ⇒ byte-identical decode to today).

### Claude's Discretion
- AO × roughness-extraction composition inside `CSNormalize` (order and divisor interaction) — the 03.1 D-08 round-trip and D-09 divisor-floor constraints must hold; research decides the math.
- Precise scalar-gate semantics for D-01 (e.g. whether a non-default `_Smoothness` scalar counts as "authored") — locked boundary: authored **map** always wins.
- Fit-driven search internals (strength ladder, iteration count, convergence criterion), blur kernel specifics, halo mitigation between blur and divide ordering.
- What `_BaseMap` binds in one-texture mode (neutral 1×1 white vs. unbound) — must reconstruct as vertex colors × neutral, identically to today's math.
- Whether the normalized Base PNG still gets **written** (unbound) in one-texture mode for the Phase-4 D-06/D-14 switch-back representation — *assumption: yes, keep writing it; binding drops it*. Confirm at plan review.
- Escape-hatch input details (texture format, binding path, default-neutral semantics) within the D-06 constraints.
- Window layout of the new controls (extraction toggle-by-strength, estimator option, offset-input affordances) within Phase-03 D-14 (functional controls only).

</decisions>

## Existing Code Insights

### Reusable Assets
- `NamerAOBaker`/`NamerAOBvh`: the sanctioned deterministic Burst-pass structure (fixed direction tables, row-slab scheduling, injectable cancellation, caller-owned `NativeArray` results) — mirror for the fit-driven extraction/search pass.
- `NamerAOPipeline`: the extraction-pipeline shape — `Extract(inspection, baseColorIn, w, h)` → pooled RT, internal low-pass, external blur controls, `ReleaseAo`, bake cache (`HasCachedBake`/`RequestBake`/`ClearBakeCache`).
- `NamerDecompPipeline.GenerateResidual`: already returns `ResidualRequired = false` / `ChosenResolution = 0` on a good fit (D-13 machinery exists); this phase changes what feeds the refit so that outcome becomes the norm for baked-response assets.
- `NamerProcessorSettings` + debounced `MarkDirty`/`Tick`: the strength + estimator controls plug in exactly like `AoUnmultiplyStrength`.
- Debug-channel toolbar (`NamerDebugChannelMaterial`): extracted-roughness visualization joins the existing roughness/AO channel views.

### Established Patterns
- GPU compute for all per-pixel texture work (NORM-03); Burst/C# for search/mesh math, deterministic and headless-testable.
- `AssetGenerator` is the only disk writer; interactive preview is memory-only (never disk).
- Settings flow: `NamerProcessorSettings` field → window control → pipeline/uniform.
- Authored-source-wins gating (03.1 D-07): authored map ⇒ byte-identical legacy path; extraction only fills absence.

### Integration Points
- `SourceInspector`/`NamerMaterialInspection`: roughness-map presence is the D-01 gate (parallel to `_OcclusionMap` for AO).
- `NamerComputePipeline.Process`: `_Roughness` scalar today — extracted roughness arrives as a texture that overrides the scalar in the pack stage.
- `NamerProcessor.Process`: extraction stage between the compute pipeline and `NamerDecompPipeline.GenerateResidual`; refit consumes the cleaned base (D-05).
- `AssetGenerator.WriteMaterial` + `NamerSurface.hlsl`: one-texture `_BaseMap` neutral binding; the D-06 optional roughness-offset input.
