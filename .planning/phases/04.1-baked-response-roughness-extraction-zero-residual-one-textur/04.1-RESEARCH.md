## Summary

Phase 04.1 takes the Phase-4 vertex-color decomposition machinery (already shipped and verified 17/17) and makes its D-13 residual auto-drop the *primary* path for assets whose base texture has material response (gloss/shading/cavity) baked in but no authored roughness map — Neo is the acceptance case. The technique is a **frequency separator**: blur the already-cleaned base so the blurred result approximates what vertex-color interpolation can hold, treat the sharp-minus-blur remainder as the baked response, route it into the 6-bit roughness field (surface PNG alpha bits 0–5), and refit the further-cleaned base into vertex colors so the residual collapses to "not required" — leaving a **one RGBA8 surface PNG + vertex-colored mesh** material with no base or residual texture bound.

**Primary recommendation:** Build the extraction as a **new GPU compute stage** (a `NAMERRoughness.compute`/`NAMERRoughness.hlsl` kernel set plus a `NamerRoughnessPipeline` mirroring `NamerAOPipeline`), slotted between `CSNormalize` (base normalization + AO un-multiply) and `CSSurfacePack` (bit packing) so the extracted per-texel roughness overwrites the `_Roughness` scalar *and* the further-cleaned base is what `VertexColorFitter` refits. Drive the **fit-driven strength search** with a deterministic CPU-Burst ladder job in the `NamerAOBaker` structural shape (off the 300 ms debounce, cached, cancellable, caller-owned buffers), and keep the **Sobel estimator** as a user-selectable Blender-parity alternative. No new packages, no format change, no runtime-decode change on the happy path (the D-06 roughness-offset input is neutral-when-unset).

Two facts materially constrain the plan and differ from the CONTEXT.md as written: (1) the Blender reference lives at `/Users/Shared/SSDevelopment/Development/GraffitiEntertainment/BlenderNamerPlugin/namer_core.py` (the CONTEXT.md path `.../namer_plugin/namer_core.py` does not exist), and (2) Blender's `extract_roughness` normalizes Sobel magnitude by the **global max** (`edge_magnitude / np.max(edge_magnitude)`), which the existing AO pipeline's *mean*-reduction does not produce — the Sobel path needs a max-reduction, while the fit-driven path deliberately avoids global normalization.

### Pattern 1: Extraction pipeline mirrors `NamerAOPipeline`
**What:** A dedicated GPU dispatch harness (`NamerRoughnessPipeline`) with staged kernels, pool-leased RTs (`R16G16B16A16_SFloat` intermediates, `R8G8B8A8_UNorm` output), a `Extract(...)`→`ReleaseRoughness(...)` contract, and a bake cache (`HasCachedBake`/`RequestBake`/`StoreBake`/`ClearBakeCache`).
**When to use:** All per-pixel roughness work — blur, Sobel, sharp-removal, remap.
**Example:** `NamerAOPipeline.Extract` at `Editor/Pipeline/NamerAOPipeline.cs` lines 79–161 is the exact structural template (staged kernels, `_compute.SetInts("_Size", …)`, `Dispatch(kernel, w, h)`, pool `Lease`/`Release`, `NewDescriptor(...enableRandomWrite=true, sRGB=false)`).

### Pattern 2: Fit-driven search mirrors `NamerAOBaker` + AO bake cache
**What:** A deterministic CPU-Burst strength-ladder job that calls the GPU per iteration (to produce the candidate cleaned base + roughness), runs the CPU refit, reads the reduced residual error, and converges on the strength minimizing it. Cancellable with an injectable headless `shouldCancel`; explicit one-time action off the 300 ms debounce; result cached so later Process calls never re-search.
**When to use:** The fit-driven estimator (D-03 default assumption); Sobel mode skips the search entirely.
**Example:** `NamerAOBaker.Bake` (fixed direction table, row-slab scheduling with `IJobParallelFor`, `EditorUtility.DisplayCancelableProgressBar` vs injected `shouldCancel`) and `NamerAOPipeline.RequestBake` (cache + `onComplete` + cancel-returns-false) — both at `Editor/Bake/NamerAOBaker.cs` and `Editor/Pipeline/NamerAOPipeline.cs`.

### Pattern 3: D-13 residual drop is already the machinery — only the input changes
**What:** `NamerDecompPipeline.GenerateResidual` already returns `ResidualRequired = false` / `ChosenResolution = 0` for a within-threshold fit on a fully-opaque base (the "no-texture endgame"). The phase re-points the refit at the post-extraction cleaned base so that outcome becomes the norm for baked-response assets.
**When to use:** The honest gate (extract → refit → drop when within threshold, else fallback).
**Example:** `GenerateResidual` step 3 (D-13 gate) at `Editor/Decompose/NamerDecompPipeline.cs` lines 230–237.

### Pattern 4: Authored-map-wins gate (D-01 mirrors 03.1 D-07)
**What:** `SourceInspector`/`NamerMaterialInspection` already gates AO extraction on `_OcclusionMap` presence. The roughness gate is the same shape on `_MetallicGlossMap` presence.
**When to use:** Decide whether extraction runs at all; authored map ⇒ byte-identical legacy path.
**Example:** `NamerComputePipeline.Process` AO three-way gate at `Editor/Pipeline/NamerComputePipeline.cs` lines 117–135.

### Anti-Patterns to Avoid
- **Extracting roughness on the pre-cleaned base:** Blender's `extract_roughness(cleaned_base)` runs *after* AO/lighting un-multiply. Extracting on the raw base would route AO gradients into roughness. Extract on `_BaseColorOut` (post-`CSNormalize`).
- **Re-deriving the packed-format math in the new kernels:** reuse `NamerEncode.hlsl` / `NamerConstants` — do not re-code `NamerPackAlphaBits` or the roughness mask.
- **Per-pixel C# loops on 2K/4K textures:** all extraction is GPU; only the strength-ladder and tiny reduce readbacks are CPU (NORM-03).
- **`System.Random` or non-deterministic search:** the fit-driven ladder must use fixed step tables and fixed float math (NamerAOBaker discipline), or headless tests become flaky.
- **Binding a 1×1 white `_BaseResidualMap` texture instead of leaving it unbound:** the shader's `{}` default is already neutral white; binding an explicit texture adds a redundant asset. Leave `_BaseResidualMap` unset (matches today's D-13 behavior).

## Common Pitfalls

### Pitfall 1: Roughness vs smoothness inversion
**What goes wrong:** The source carries *smoothness* (`_Smoothness` scalar, `_MetallicGlossMap.a`), while the packed field stores *roughness* (`roughness = 1 - smoothness`). Extracted roughness from edge magnitude is already in roughness domain — a `1 - edge` slip silently flips glossy to matte.
**Why it happens:** `SourceInspector.FinalizeInspection` does `Roughness = 1f - Smoothness`; `CSNormalize` does the same for the map path. The extraction is a *third* roughness source and must land in the same `[0,1]` roughness domain without another inversion.
**How to avoid:** Extraction kernels emit roughness directly; the pack consumes `.y` of `_PackInputs` as roughness (no inversion). Add a golden-vector/round-trip test: a uniform edge → roughness ~0, a sharp edge → roughness high.
**Warning signs:** Extracted assets render opposite gloss; debug "Roughness" channel (index 4) inverted vs source.

### Pitfall 2: AO × roughness composition order (D-03 discretion, 03.1 D-08/D-09)
**What goes wrong:** Both AO un-multiply (`CSNormalize`) and roughness extraction remove baked response from the base. If extraction runs on the *pre*-un-multiply base, AO gradients leak into roughness; if the extracted roughness itself gets un-multiplied, the D-08 round-trip (`base_unmul × ao ≈ base`) breaks.
**Why it happens:** Two "un-bake" stages on the same texture; the 03.1 divisor-floor 0.1 (D-09) must hold for the AO divisor and the extracted-roughness path must not re-trigger it.
**How to avoid:** Fixed order: `CSNormalize` (AO un-multiply with the 0.1 floor) → extraction reads `_BaseColorOut` → writes roughness + further-cleaned base. Research decides the exact divisor interaction, but the *ordering* is locked (extraction-after-AO, matching Blender).
**Warning signs:** AO and roughness both darkened; `_AoUnmultiplyFloor` interplay producing >10% darkening.

### Pitfall 3: Blender's global-max Sobel normalization
**What goes wrong:** Blender's `extract_roughness` divides Sobel magnitude by `np.max(edge_magnitude)` — a *global maximum* over the whole texture. A per-texel normalize (or no normalize) produces a different roughness distribution, and a *mean* normalize (the `.r` channel of the existing `CSReduce`) distorts it.
**Why it happens:** The existing `CSReduce` is a 4-channel reduce whose `.g` channel is ALREADY a hierarchical **max** (and `.r` a mean), but it is wired to the vertex-color decomposition error stats, not to Sobel magnitude — so the Sobel path needs its own max-reduce *target* for the edge-magnitude field, not a new reduction primitive.
**How to avoid:** `CSRoughnessMaxReduce` reuses the `CSReduce` `.g = max` hierarchical body (copy the overflow-free 8x8 block-max loop + the `src.x < _AvgSrcSize.x && src.y < _AvgSrcSize.y` guards, writing the global max into a tiny RT); the fit-driven path does not need it. Note the global max also makes the Sobel scale-invariant (any constant kernel scale cancels in `x/max(x)`), so a plain 3×3 Sobel achieves parity without scipy's exact scaling.
**Warning signs:** Extracted roughness uniformly low/high (bad max), or a faint uniform wash where the global max was dominated by one strong edge.

### Pitfall 4: Rec.601 vs Rec.709 luminance
**What goes wrong:** Blender's `extract_roughness` uses Rec.601 weights `0.299/0.587/0.114`; the Unity AO path (`NAMERAO.hlsl`) uses Rec.709 `0.2126/0.7152/0.0722`. Using Rec.709 in the Sobel estimator breaks byte-level Blender parity; using Rec.601 in AO would break the existing AO.
**Why it happens:** Two luminance conventions coexist in the codebase; the roughness kernels are new and could copy the wrong one.
**How to avoid:** `NAMERRoughness.hlsl` defines its own Rec.601 constant set (Blender parity) and does NOT reuse `NAMER_LUMA_*`. Flag in code comments that this divergence is intentional for parity.
**Warning signs:** Sobel-mode extraction differs from a Blender fixture on the same input.

### Pitfall 5: Halo / ringing at blur boundaries (blur-before-vs-after ordering)
**What goes wrong:** The `cleanedBase = base - strength·(base - blurredBase)` sharp-removal produces halos at strong edges (the same class of artifact 03.1 handled for AO un-multiply).
**Why it happens:** `base - blurred` overshoots where the blur smears a sharp edge; the residual then carries the overshoot.
**How to avoid:** Blur-before-subtract ordering + clamp the removed detail, and let the fit-driven search *measure* the resulting residual (which naturally penalizes halos). This is the D-03 Claude's-Discretion "halo mitigation between blur and divide ordering" — resolve it with the search as the arbiter.
**Warning signs:** Bright/dark fringes around high-contrast features in the one-texture result.

### Pitfall 6: One-texture binding must not regress D-14 switch-back
**What goes wrong:** In one-texture mode the base PNG is *written* (for switch-back) but *not bound*; if `WriteMaterial` instead binds the base PNG, the material renders `vertexColor × basePNG` — double-applying the low-frequency color.
**Why it happens:** `baseResidualPath = decomp != null ? residualWritePath : basePath`; the one-texture case needs `baseResidualPath = null` *while still writing* the base PNG.
**How to avoid:** Keep `WriteBaseTexture` unconditional; set `_BaseResidualMap` only when a residual is actually required (or when decomp is null). Confirm the "still write the Base PNG" assumption (D-06/D-14 switch-back) at plan review — currently an assumption, not a decision.
**Warning signs:** One-texture asset brighter/darker than the preview (base applied twice); switch-back toggle reprocesses.

### Pitfall 7: 6-bit roughness quantization underfits per-texel detail (why D-06 exists)
**What goes wrong:** The extracted roughness is quantized to 64 levels (`floor(roughness * 63)`); per-texel gloss variation finer than 1/63 is lost. That's fine for the happy path but is the exact gap the escape hatch exists to close.
**Why it happens:** `NamerPackAlphaBits` floors to 6 bits by design (ENCD-02).
**How to avoid:** D-06 offset input is the fallback — an optional single RGBA texture that *offsets* decoded roughness, neutral-when-unset so the happy path decode is byte-identical. Document the offset must be *additive to decoded roughness* (not a replacement) to preserve the "unset ⇒ identical" contract.
**Warning signs:** A baked-response asset whose gloss detail still inflates the residual after extraction — route to the escape hatch rather than forcing the residual.

## Code Examples

### Roughness extraction: Blender-parity Sobel (illustrative, mirrors `namer_core.py extract_roughness`)
```hlsl
// NAMERRoughness.hlsl — Rec.601 luminance + Sobel edge magnitude (Blender parity).
// Blender: lum = 0.299R + 0.587G + 0.114B; sobel_x = sobel(lum, axis=1);
// sobel_y = sobel(lum, axis=0); edge = sqrt(x²+y²); roughness = clip(edge / max(edge)).
static const float NAMER_ROUGH_LUMA_R = 0.299;   // intentionally NOT Rec.709 (Pitfall 4)
static const float NAMER_ROUGH_LUMA_G = 0.587;
static const float NAMER_ROUGH_LUMA_B = 0.114;

float NamerRoughnessLuminance(float3 c) { return dot(c, float3(NAMER_ROUGH_LUMA_R, NAMER_ROUGH_LUMA_G, NAMER_ROUGH_LUMA_B)); }

// 3x3 Sobel on the cleaned-base luminance; magnitude goes to a separate max-reduce
// kernel that normalizes by the GLOBAL max (Blender's np.max), not a per-texel divide.
[numthreads(8,8,1)]
void CSRoughnessSobel(uint3 id : SV_DispatchThreadID)
{
    if (id.x >= _Size.x || id.y >= _Size.y) return;
    int2 p = (int2)id.xy;
    float l = NamerRoughnessLuminance(_BaseColorOut[p].rgb);
    // Gx (horizontal edges) and Gy (vertical edges), 3x3 Sobel.
    float gx = -l(off) ... ;   // horizontal kernel  [-1 0 1; -2 0 2; -1 0 1]
    float gy = ...;            // vertical kernel    [-1 -2 -1; 0 0 0; 1 2 1]
    _RoughnessRaw[p] = float4(sqrt(gx*gx + gy*gy), 0.0, 0.0, 1.0);
    // A separate CSRoughnessMaxReduce normalizes: roughness = saturate(mag / globalMax).
}
```
Source of the operator definition: [CITED: en.wikipedia.org/wiki/Sobel_operator] (Gx `[[-1,0,1],[-2,0,2],[-1,0,1]]`, Gy `[[-1,-2,-1],[0,0,0],[1,2,1]]`); Blender math read from the reference [VERIFIED: namer_core.py `extract_roughness` lines 62–71].

### CSNormalize integration: roughness texture overrides the scalar
```hlsl
// NAMERPack.compute — CSNormalize gains a third roughness source (extraction).
// Existing: _HasMetallicGlossMap -> map-derived; else scalar _Roughness.
// New:       _HasExtractedRoughness -> _RoughnessTex[id.xy] (blended by strength).
Texture2D<float4> _RoughnessTex;   // per-texel extracted roughness (R channel, linear)
float _HasExtractedRoughness;
float _RoughnessExtractStrength;   // D-02 user override (0 = off)

// inside CSNormalize, after the map/scalar branches:
if (_HasExtractedRoughness > 0.5)
{
    roughness = lerp(_Roughness, _RoughnessTex[id.xy].r, _RoughnessExtractStrength);
}
_PackInputs[id.xy] = float4(metallic, roughness, _Emissive, 1.0);
```
The extraction *also* writes the further-cleaned base back into `_BaseColorOut` (the refit target), so the same dispatch both routes gloss into roughness and removes it from the base.

### D-06 roughness-offset decode (neutral-when-unset)
```hlsl
// NamerSurface.hlsl — NAMER_DECODE_SURFACE, roughness gains an optional additive offset.
TEXTURE2D(_RoughnessOffsetMap);  SAMPLER(sampler_RoughnessOffsetMap);
// Unset/unbound => "black" {} default => offset 0 => byte-identical decode (white would sample .r == 1 and saturate roughness — non-neutral for an additive offset).

// after: roughness = (float)(a & 0x3Fu) / 63.0;
roughness = saturate(roughness + SAMPLE_TEXTURE2D(_RoughnessOffsetMap, sampler_RoughnessOffsetMap, uv).r);
smoothness = 1.0 - roughness;
```

## Open Questions (RESOLVED — see 04.1-01/04.1-02 PLAN.md decisions)

All four open questions are substantively resolved in the plan decisions below; they are retained for provenance only.

1. **Fit-driven vs Sobel default (A1)** — RESOLVED
   - What we know: D-03 ships both as a selectable option and names fit-driven as the default *assumption to confirm at plan review*.
   - Resolution: fit-driven is the default (`NamerRoughnessEstimator.FitDriven = 0`, `DefaultRoughnessEstimator = 0`); Sobel = 1 for Blender parity. See 04.1-01 `<decisions>` (D-03 default = fit-driven) and 04.1-02 Task 3.

2. **Scalar-gate semantics for D-01 (A4)** — RESOLVED
   - What we know: locked boundary is "authored *map* always wins".
   - Resolution: `MetallicGlossMap == null` is the sole extraction trigger; a non-default `_Smoothness` scalar does NOT gate it off (it blends via `_RoughnessExtractStrength`). See 04.1-01 `<decisions>` (D-01 scalar-gate semantics).

3. **AO × roughness divisor composition (D-03 discretion)** — RESOLVED
   - What we know: extraction must run after `CSNormalize` AO un-multiply; 03.1 D-08 round-trip and D-09 0.1 floor must hold.
   - Resolution: locked order = extraction-after-AO (A6); the fit-driven search's residual measurement is the arbiter for any remaining ambiguity. See 04.1-01 `<decisions>`.

4. **Strength ladder granularity + convergence** — RESOLVED
   - What we know: fit-driven internals are Claude's Discretion.
   - Resolution: fixed deterministic ladder `{0.0, 0.15, 0.3, 0.5, 0.7, 0.9, 1.0}` with the residual `MaxError` as the objective (the 0.0 step makes no-response assets no-op). See 04.1-02 Task 1 `StrengthLadder`.
