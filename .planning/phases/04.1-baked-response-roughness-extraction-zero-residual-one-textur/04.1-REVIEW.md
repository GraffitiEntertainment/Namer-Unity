## Summary

Phase 04.1 (including the carried-in Phase 4 decomposition work on this branch) is substantially sound: asset-safety confinement in `AssetGenerator` is layered and correct (destination validation, per-path re-validation, prefix/suffix rejection, stamped-overwrite gate — no path can escape `Assets/` and source assets are never mutated); GPU/CPU ownership of render targets is carefully tracked through the pool, `NamerComputeResult`, and the roughness-pool handoff; the compute kernels' bounds guards, dispatch math (`(w+7)/8` vs `[numthreads(8,8,1)]`), and reduce ping-pong are all correct; and the working-tree `FitOnlyMaxError` change is a genuine improvement (the with-residual `MaxError` is indeed vacuous as a search objective). The previously-fixed CR/WR items (CR-01 multi-mesh guard, WR-01 readback dispose, WR-02 threshold-keyed cache) verify as fixed.

Five Warnings remain, none of which corrupt output on the default happy path: two are stale-state hazards (fit-cache key, shared raw-copy material keyword), one is an error-path render-target leak in the long-lived preview pipeline, one is the unwired off-debounce fit API leaving the search inside the debounced recompute with a progress bar, and one is a vacuous test loop that claims to prove D-06 neutral decode but never touches the shader. No Critical findings; verdict NEEDS FIXES per the "any Critical/Warning" rule.

Items reviewed and deliberately **not** flagged (documented/intentional per phase context): white-occlusion fixture isolation (D-07), `FitOnlyMaxError` vs `MaxError` gating semantics, AO three-way gate and un-multiply-on-extract, Sobel flat-base-yields-glossy behavior (Blender parity), failed-fit still extracting at max strength (honest gate keeps the residual), cancel-falls-back-to-identity contract, and the base PNG still written but unbound in one-texture mode.

## Warnings

### WR-01: Fit-driven strength cache key omits the base-map/AO inputs — stale strength reused in the processor window

**File:** `Packages/com.graffitientertainment.namer/Editor/Pipeline/NamerRoughnessPipeline.cs:508-513` (key), `:71-72` (cache), `Packages/com.graffitientertainment.namer/Editor/UI/NamerEditorWindow.cs:39,416-424,348`
**Issue:** The 3A fit cache is keyed on `(meshId, estimator, w, h, maxErrorThreshold)`. The search objective, however, depends on the base texture content and the AO normalization feeding the refit — neither is in the key. `NamerProcessor.Process` creates a fresh `NamerComputePipeline` per call (safe), but the window's `_pipeline` (and its roughness fit cache) lives from `OnEnable` to `OnDisable` and survives selection changes (`OnSelectionChanged` → `RebuildInspection` never clears it). Selecting asset A (mesh M, base 1024x1024, optimal strength 0.7) and then asset B (same mesh M, same base dimensions, different base texture — e.g. a re-skinned prop sharing the mesh, or the same asset after the user retunes `AoUnmultiplyStrength`/`AoContrast`, which changes the normalized base) returns A's cached strength for B's fit. The preview then applies the wrong extraction strength silently (wrong packed roughness, wrong cleaned base, wrong residual collapse).
**Fix:** Include the objective-relevant identity in the key, e.g. add `inspection.BaseMap` instance ID and the AO controls (or a content/setting revision) to `MakeFitKey`; or clear the cache when the window's selection changes:

```csharp
private static (int, int, int, int, int, float) MakeFitKey(
    NamerMaterialInspection inspection, int w, int h, float maxErrorThreshold)
{
    int meshId = inspection.BakeSourceMesh != null ? inspection.BakeSourceMesh.GetInstanceID() : 0;
    int baseMapId = inspection.BaseMap != null ? inspection.BaseMap.GetInstanceID() : 0;
    return (meshId, baseMapId, (int)inspection.RoughnessEstimator, w, h, maxErrorThreshold);
}
```

### WR-02: `Resample` blits through the shared static raw-copy material without controlling `_REENCODE_SRGB` — residual data gamma-corrupts if the keyword was left enabled

**File:** `Packages/com.graffitientertainment.namer/Editor/Decompose/NamerDecompPipeline.cs:515-520`; state mutated at `Packages/com.graffitientertainment.namer/Editor/Pipeline/NamerComputePipeline.cs:428-440`, `Packages/com.graffitientertainment.namer/Editor/Generation/AssetGenerator.cs:113-116`, `Packages/com.graffitientertainment.namer/Editor/UI/NamerEditorWindow.cs:482-485`
**Issue:** `Resample` does `Graphics.Blit(source, dst, NamerComputePipeline.RawCopyMaterial())` — a shared static material whose `_REENCODE_SRGB` keyword is toggled by unrelated callers. If the keyword is enabled when `Resample` runs, every residual down/up-sample applies the IEC linear→sRGB encode to linear float residual data, silently corrupting `ChooseResolution`'s evaluation and the saved reduced-resolution residual EXR. Today the keyword happens to be disabled at every `Resample` call site only because the last `Upload` inside `NamerComputePipeline.Process` is always the metallic/gloss upload (linear for both authored masks and the neutral fill) — but a metallic/gloss (or occlusion, via AO `BakeAndUpload` ordering changes) map imported with sRGB ON, or any future reordering of the upload sequence, flips the keyword and corrupts assets with no error. This is a latent, order-dependent data-corruption hazard on a shared-static side channel.
**Fix:** Make `Resample` independent of prior keyword state — explicitly disable the keyword around the blit (mirroring `AssetGenerator.Generate`'s enable→blit→disable discipline), or give the decomp pipeline its own keyword-free copy material:

```csharp
private RenderTexture Resample(RenderTexture source, int dstW, int dstH)
{
    RenderTexture dst = _pool.Lease(NewDescriptor(dstW, dstH, GraphicsFormat.R16G16B16A16_SFloat));
    Material rawCopy = NamerComputePipeline.RawCopyMaterial();
    bool wasEnabled = rawCopy.IsKeywordEnabled(NamerComputePipeline.ReencodeSrgbKeyword);
    rawCopy.DisableKeyword(NamerComputePipeline.ReencodeSrgbKeyword);
    Graphics.Blit(source, dst, rawCopy);
    if (wasEnabled) { rawCopy.EnableKeyword(NamerComputePipeline.ReencodeSrgbKeyword); }
    return dst;
}
```

### WR-03: Exception paths leak leased render targets in the long-lived window pipeline

**File:** `Packages/com.graffitientertainment.namer/Editor/Pipeline/NamerComputePipeline.cs:196-223` (Process finally), `Packages/com.graffitientertainment.namer/Editor/Pipeline/NamerRoughnessPipeline.cs:279-309` (ExtractSobel finally)
**Issue:** If an exception propagates out of `NamerComputePipeline.Process` after the leases (e.g. `InvalidOperationException` from a failed GPU readback inside the fit-driven evaluate callback, or from `ReadBackGlobalMax`), the `finally` block releases the inputs but not `surfaceOut` or `baseColorOut` (released only via `ReleaseResult`/the `cleanedBase != null` branch, neither reached on throw). Same pattern in `NamerRoughnessPipeline.ExtractSobel`: `roughnessOut` is leased but not released in the `finally` when `ReadBackGlobalMax` throws. In `NamerProcessor.Process` the `finally` disposes the whole pipeline, so the pooled RTs are destroyed — no lasting leak. But the editor window keeps `_pipeline` alive across recomputes: each failed `RecomputePreview` (caught at `NamerEditorWindow.cs:403`) permanently strands 2+ live RTs in the pool until the window closes, growing GPU memory on repeated failures and breaking the `LiveRenderTargetCount`-returns-to-baseline watchdog contract.
**Fix:** Release the not-yet-returned leases in the exception path — e.g. track completion and release `surfaceOut`/`baseColorOut` (compute pool) and `roughnessTex`/`cleanedBase` (roughness pool) in the `finally` when the result was not returned, and add `Release(roughnessOut)` to `ExtractSobel`'s `finally` on the throw path (a `returned` flag or try/fault pattern).

### WR-04: Fit-driven strength search runs inside the 300 ms-debounced preview recompute with a cancelable progress bar; the off-debounce `RequestFit` API built for this is dead code

**File:** `Packages/com.graffitientertainment.namer/Editor/UI/NamerEditorWindow.cs:348` (`_pipeline.Process(inspection, evaluate, null, _errorThreshold)` inside the debounced `RecomputePreview`), `Packages/com.graffitientertainment.namer/Editor/Bake/NamerRoughnessFitter.cs:85-90` (progress bar when `shouldCancel == null`), `Packages/com.graffitientertainment.namer/Editor/Pipeline/NamerRoughnessPipeline.cs:208-248` (`RequestFit` — zero callers), `Packages/com.graffitientertainment.namer/Editor/Pipeline/NamerComputePipeline.cs:321-326` (`HasCachedFit` — zero callers)
**Issue:** D-04 specifies the fit-driven pass as "an explicit one-time action off the 300 ms debounce" and `NamerRoughnessPipeline.RequestFit` was built as that vehicle (mirroring `NamerAOPipeline.RequestBake`), but nothing calls it — `RecomputePreview` passes the evaluate callback straight into `Process` with `shouldCancel: null`, so on every cache miss the search (up to 7 GPU sharp-removals + readbacks + refits + residual generations) runs synchronously inside the debounced slider recompute and `NamerRoughnessFitter.Fit` pops `EditorUtility.DisplayCancelableProgressBar` per recompute. Dragging the strength/threshold sliders repeatedly on a cache-missing asset re-runs the full search each debounce tick with a flashing progress bar. The dead public API (`RequestFit`, `NamerComputePipeline.HasCachedFit`, and the `maxErrorThreshold` plumbing duplicated for it) is misleading surface area.
**Fix:** Either wire the intended pattern (window calls `RequestFit` off-debounce like the AO bake, then `RecomputePreview` hits the cache), or at minimum pass a `shouldCancel` delegate from the window and remove the unused `RequestFit`/`HasCachedFit` API until it has a caller.

### WR-05: D-06 neutrality test's decode-identity loop is tautological — it can never fail and never touches the shader

**File:** `Packages/com.graffitientertainment.namer/Tests/Editor/NamerOneTextureTests.cs:150-156`
**Issue:** `RoughnessOffset_Unset_DecodesIdentical` claims to prove "unset (black) offset decodes roughness byte-identically", but the loop asserts `roughness == Mathf.Clamp01(roughness + 0f)` — an arithmetic tautology true for every `x ∈ [0,1]`, computed entirely in C#. The shader is never sampled, so the property the test claims to guard (the `"black" {}` property default sampling `.r == 0`) is not machine-verified: changing the shader default to `"white" {}` — which would saturate every unset material's roughness to 1.0, exactly the regression the test's own comment describes — still passes this test. Only the property-existence checks (lines 132-143) are real.
**Fix:** Replace the loop with a check that actually pins the shader-side default, e.g. assert the shader's declared property default texture name via `shader.GetPropertyCount`/`GetPropertyTextureDefaultName` (Unity 2021.2+ / Unity 6 API), or render a 1x1 quad through the material with an unbound slot and compare the output against the pre-04.1 decode values.

### IN-03: Debug channel 0 "Base Color" displays the residual when one is bound

**File:** `Packages/com.graffitientertainment.namer/Shaders/NamerDebugView.shader:103-106,131-134`
**Issue:** Channel 0 (Base Color) and channel 7 (Residual) both display `baseResidual.rgb`. In decomposed mode the window binds `_BaseResidualMap` to the residual, so the "Base Color" view silently shows the residual texture — while `_DebugBaseMap` (bound to the actual base at `NamerEditorWindow.cs:386,394`) holds exactly the intended data and is only used by the heatmap channel.

### IN-05: Heatmap normalizer `0.25` duplicated as a magic number in the debug shader, and it diverges from the compute path's rule

**File:** `Packages/com.graffitientertainment.namer/Shaders/NamerDebugView.shader:143`; compare `Packages/com.graffitientertainment.namer/Editor/Decompose/NamerDecompPipeline.cs:93,212`
**Issue:** The debug heatmap hardcodes `err / 0.25` while the compute path uses `_MaxObservedErr = max(threshold, kMaxObservedErrFloor=0.25)`. Identical at the default threshold (0.02) but diverges when a user raises ErrorThreshold above 0.25 (slider max 0.10 — so currently unreachable; still a drift risk). The `NAMER_DECOMP_HEATMAP` include is the shared home; the normalizer bound is not shared.
**Fix:** Either pass the same `max(_Threshold, 0.25)` bound into the debug material as a float, or add a named `static const float` in `NAMERDecomp.hlsl` used by both (compute already uploads it as a uniform; the debug shader can keep 0.25 but reference a documented constant).

### IN-06: Zero-filled tangent/UV fallbacks in the splitter change attribute semantics for attribute-less meshes

**File:** `Packages/com.graffitientertainment.namer/Editor/Decompose/MeshVertexSplitter.cs:81-91`
**Issue:** When the source mesh lacks tangents/UVs, the splitter substitutes all-zero arrays rather than leaving the streams absent. A zero tangent stream (`w == 0`) written to the split mesh can defeat the SRP's derive-from-derivatives TBN fallback that an attribute-less mesh would otherwise get, and all-zero UVs guarantee `CannotDecompose` (single-texel coverage). For imported FBX assets (always tangent/UV-complete) this never triggers; it only affects procedurally-built meshes.
**Fix:** Consider propagating "stream absent" (null) through `NamerSplitResult` and skipping the corresponding `SetTangents`/`SetUVs` in `BuildSplitMesh`/`BuildPreviewSplitMesh`, or at least document the zero-fill consequence at the fallback site.

### IN-07: `BuildPreviewSplitMesh` duplicates `AssetGenerator.BuildSplitMesh`

**File:** `Packages/com.graffitientertainment.namer/Editor/UI/NamerEditorWindow.cs:598-633`; twin at `Packages/com.graffitientertainment.namer/Editor/Generation/AssetGenerator.cs:511-545`
**Issue:** ~30 lines of mesh-building (attribute streams, index format, bindposes-before-boneWeights, sub-meshes, bounds) are copy-pasted between the window preview and the generator. The bindposes-order fix (gap 3b) already had to be applied in both places — the exact drift failure mode duplication invites.
**Fix:** Extract a shared `NamerMeshBuilder.BuildSplitMesh(NamerSplitResult, Color32[], string name)` used by both callers (the preview variant only adds `hideFlags` and skips the asset write).

## Dispositions

_Resolved 2026-09-15 during the 04.1 `--gaps-only` gate pass. Fixes verified by a clean recompile + full EditMode regression (118/118) in the live editor._

### WR-01 — FIXED

`MakeFitKey` widened to a 10-element key: `(meshId, baseMapId, aoStrength, aoContrast, aoBlurRadius, aoUnmultiplyStrength, estimator, w, h, maxErrorThreshold)` (`NamerRoughnessPipeline.cs`, both call sites now `var key = MakeFitKey(inspection, w, h, maxErrorThreshold);`). The key now identifies everything the fit objective reads: the mesh UVs, the base-map **content** (instance ID), the four AO controls, the estimator, and the dimensions/threshold. The dead `HasCachedFit` API named in WR-04 was deleted from both `NamerRoughnessPipeline.cs` and its `NamerComputePipeline.cs` forwarder (zero callers).

### WR-02 — FIXED

`NamerDecompPipeline.Resample` now disables `_REENCODE_SRGB` on the shared raw-copy material before the blit. Chosen variant: disable-without-restore (not the reviewer's save/restore) — every other caller (`NamerComputePipeline.Upload`) explicitly sets the keyword state it needs immediately before its own blit, so "callers own the keyword at blit time" is the maintained invariant and no restore is required. Resampled residual data is definitionally linear, so the keyword is always off here.

### WR-03 — FIXED

Exception-path lease releases added via catch-rethrow (clearer ownership split than a `returned` flag — `finally` keeps the inputs, the catch owns the un-returned outputs):

- `NamerComputePipeline.Process`: on a mid-pipeline throw, releases `surfaceOut` (compute pool), `roughnessTex` and `cleanedBase` via `ReleaseExtractedRoughness` (roughness-pool-owned — a compute-pool `Release` would silently no-op on foreign targets), and `baseColorOut` (compute pool) only when no `cleanedBase` has replaced it yet — preserving the same either/or ownership the success path's finally uses, so nothing is double-released.
- `NamerRoughnessPipeline.ExtractSobel`: `roughnessOut` released in a catch before the rethrow (the finally only owns intermediates).

### WR-04 — ACCEPTED (documented decision)

The option-1 preview wiring is a recorded phase decision (STATE.md key decisions: "Preview wiring = option 1 — RecomputePreview supplies the 3A evaluate callback"), not an oversight. With WR-01's keyed cache the search runs once per distinct key (asset + AO settings + mesh + dimensions + threshold); subsequent debounced recomputes hit the cache with no progress bar. Known accepted cost: AO controls are part of the key, so a *continuous drag* of an AO slider re-keys per debounce tick and can re-fire the cancelable search; passing a `shouldCancel` delegate from the window is noted for a future UX pass. `RequestFit` is retained as the 3A public API (mirrors `NamerAOPipeline.RequestBake`); the genuinely dead `HasCachedFit` half of the finding was removed under WR-01.

### WR-05 — FIXED

The tautological `roughness == Clamp01(roughness + 0f)` loop in `RoughnessOffset_Unset_DecodesIdentical` replaced with `shader.GetPropertyTextureDefaultName(shader.FindPropertyIndex("_RoughnessOffsetMap")) == "black"` — pinning the shader's **declared** property default, so a `{}` default regression (e.g. `"white" {}`) now fails the test instead of silently passing. The arithmetic-neutral decode argument remains in the comment as design context.

### IN-01 … IN-07 — NOTED, not fixed

All seven Info findings are recorded above for the backlog. None corrupt output on reachable paths (IN-02/IN-04 are dead code/doc drift; IN-03/IN-05 are display-only with unreachable divergence at current slider bounds; IN-06 affects only attribute-less procedural meshes; IN-07 is duplication debt). Fixing them is out of scope for this gap-closure pass.
