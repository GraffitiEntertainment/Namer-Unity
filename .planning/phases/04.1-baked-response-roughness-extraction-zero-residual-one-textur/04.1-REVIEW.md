# Phase 04.1: Code Review Report

**Reviewed:** 2026-09-06
**Depth:** standard
**Files Reviewed:** 21
**Status:** issues_found

## Summary

Phase 04.1 adds the Sobel roughness estimator, the fit-driven strength-ladder search
(`NamerRoughnessFitter`), the frequency-separation compute kernels (blur H/V -> sharp-detail ->
sharp-removal -> remap), the D-01/D-05/1A/3A pipeline gates, the D-07 foldout/scroll window
restructure, and the D-06 `_RoughnessOffsetMap` shader input. The overall architecture is
coherent and the ownership/disposal contracts for the new render targets are carefully traced
and correct on the happy paths.

One critical defect exists in the surface-pack gate: the pipeline flags `_HasExtractedRoughness`
off the *intent* (`shouldExtract`) rather than the *result* (whether an extracted-roughness
texture was actually produced). In the default configuration (decomposition OFF, roughness
extraction ON at strength 1, fit-driven estimator), no extraction runs because the fit-driven
path requires a refit objective, yet the pack still lerps the scalar roughness toward the white
fill — forcing every texel's roughness to its maximum and silently discarding the source
smoothness. Two further warnings (a `NativeArray` leak in the Sobel global-max readback, and a
fit cache keyed without the error threshold) and three informational items round out the review.

## Critical Issues

### CR-01: Default/identity path forces packed roughness to 1.0 (discards source smoothness)

**File:** `Packages/com.graffitientertainment.namer/Editor/Pipeline/NamerComputePipeline.cs:180-182` (and `Packages/com.graffitientertainment.namer/Compute/NAMERPack.compute:115-118`)

**Issue:** `BindAndDispatchSurfacePack` receives `shouldExtract` (the *intent* flag, computed as
`MetallicGlossMap == null && RoughnessExtractStrength > 0`) as its `hasExtractedRoughness`
parameter, not whether a roughness texture was actually produced. In the "identity legacy path"
(`shouldExtract && isFitDriven` but `BakeSourceMesh == null` or `evaluate == null` — which is the
**default** configuration: decomposition OFF, extraction ON, fit-driven), `roughnessTex` stays
null, so the pack binds `WhiteFill()`. The kernel then executes:

```hlsl
if (_HasExtractedRoughness > 0.5) {
    roughness = lerp(roughness, _RoughnessTex[id.xy].r, _RoughnessExtractStrength);
}
```

With `_HasExtractedRoughness == 1`, `_RoughnessTex.r == 1.0` (white fill), and the default
`_RoughnessExtractStrength == 1.0`, every texel's packed roughness becomes `1.0`, completely
discarding the source `_Roughness`/smoothness. The same corruption occurs when a fit-driven
search is cancelled (`fit.Cancelled` returns a null-roughness result) or when the CR-01
multi-material guard nulls the source mesh mid-Process — the comment at line 177 mislabels this
path as "identity", but it is not identity: it silently maxes out roughness on the generated
material. This affects both the live preview (`NamerEditorWindow.RecomputePreview` calls
`Process(inspection)` with no evaluate) and real generation.

**Fix:** Gate `_HasExtractedRoughness` on the actual texture, not the intent:

```csharp
BindAndDispatchSurfacePack(octahedral, packInputs, surfaceOut,
    roughnessTex != null ? (Texture)roughnessTex : WhiteFill(),
    roughnessTex != null,                       // <-- hasExtractedRoughness = a real result
    inspection.RoughnessExtractStrength, w, h);
```

The existing `roughnessTex != null ? roughnessTex : WhiteFill()` selection already encodes the
correct condition; the second argument should reuse it instead of `shouldExtract`. With
`_HasExtractedRoughness == 0` the kernel leaves the scalar roughness untouched, restoring the
intended identity fallback.

## Warnings

### WR-01: `ReadBackGlobalMax` never disposes its `NativeArray<float>`

**File:** `Packages/com.graffitientertainment.namer/Editor/Pipeline/NamerRoughnessPipeline.cs:467-479`

**Issue:** `request.GetData<float>()` returns a `NativeArray<float>` that must be disposed, but
the method returns without disposing it. Every Sobel extraction leaks one native allocation
(the global-max reduce readback), which trips Unity's leak-detection (an error-level
"NativeArray has been allocated ... but not disposed" log) and leaks memory across repeated
preview recomputes. This is the same resource contract the neighboring
`AssetGenerator.ReadBackResidual` honors with a `finally { data.Dispose(); }`, but it is missing
here.

**Fix:** Wrap the scan and dispose:

```csharp
NativeArray<float> data = request.GetData<float>();
try
{
    float globalMax = 0f;
    for (int y = 0; y < validHeight; y++)
        for (int x = 0; x < validWidth; x++)
        {
            int index = (y * src.width + x) * 4 + 1;
            globalMax = Mathf.Max(globalMax, data[index]);
        }
    return globalMax;
}
finally
{
    data.Dispose();
}
```

### WR-02: Fit cache is keyed without the error threshold and caches failed fits

**File:** `Packages/com.graffitientertainment.namer/Editor/Pipeline/NamerRoughnessPipeline.cs:482-486` (key), `321-335` (`ExtractFitDriven`), `202-235` (`RequestFit`)

**Issue:** `MakeFitKey` keys the fit cache on `(meshId, estimator, w, h)` only. The
`maxErrorThreshold` is not part of the key, and both `ExtractFitDriven` and `RequestFit` cache
the `NamerRoughnessFitResult` even when `Passed == false`. A later reuse of a cached fit under a
different error threshold (or a cached failed search) returns a stale `Strength` instead of
re-searching. This is currently latent because `NamerProcessor.Process` constructs a fresh
`NamerComputePipeline` per call (so the main generation path never reuses the cache), but the
public `HasCachedFit`/`RequestFit` surface exposes the interactive path where a threshold change
would silently reuse a strength fit against a different target.

**Fix:** Include `maxErrorThreshold` in the cache key, or do not cache `Passed == false` results
(re-search on the next request), and document the threshold-dependency of the cached value.

## Info

### IN-01: Stale debug-channel range in `NamerDebugChannelMaterial.SetChannel` docs

**File:** `Packages/com.graffitientertainment.namer/Editor/UI/NamerDebugChannelMaterial.cs:77`

**Issue:** The XML doc reads "Selects the debug channel (0..8 per the UI-SPEC debug channel
contract)" but the shader now accepts 0..9 (the appended "Extracted Roughness" channel). Harmless
doc drift; update to 0..9 to avoid misleading the next reader.

**Fix:** Update the comment to "0..9".

### IN-02: Misleading "identity legacy path" comment masks CR-01

**File:** `Packages/com.graffitientertainment.namer/Editor/Pipeline/NamerComputePipeline.cs:177`

**Issue:** The comment `// else: identity legacy path — fit-driven without a refit (1A) or
strength == 0.` is inaccurate twice over: `strength == 0` never reaches this branch (it is
excluded by `shouldExtract`), and the branch is not identity (see CR-01 — it maxes roughness).
Fixing the comment in tandem with CR-01 prevents the same misreading from recurring.

**Fix:** Rewrite to describe the actual fallback (e.g., "fit-driven without a refit objective —
extraction is skipped and the scalar roughness is preserved").

### IN-03: `baseColorOut` leaks on exception in the non-fit-driven path

**File:** `Packages/com.graffitientertainment.namer/Editor/Pipeline/NamerComputePipeline.cs:196-223`

**Issue:** In `Process`, the `finally` block releases `baseColorOut` only when `cleanedBase !=
null`. On the success path `baseColorOut` is returned as `NormalizedBaseColor`, so that is
correct; but if `ExtractRoughness` throws mid-Process (e.g. a GPU/shader failure) before the
result is returned, `cleanedBase` is still null and `baseColorOut` is never returned to the pool.
The leak is bounded by pipeline disposal in the `NamerProcessor` path, but in the long-lived
window pipeline a repeated preview failure accumulates live targets.

**Fix:** On the exception path only, release `baseColorOut` in `finally` (e.g. track a
`resultReturned` flag, or release `baseColorOut` when an exception is being propagated and
`cleanedBase == null`).
