# Phase 04.1: Code Review Report

**Reviewed:** 2026-09-16T20:24:52Z
**Depth:** standard
**Files Reviewed:** 23
**Status:** issues_found

## Summary

Phase 04.1 adds baked-response roughness extraction: a Rec.601-luminance Sobel estimator
(`NAMERRoughness.compute`, hierarchical 8x8 block-max reduce, robust p90 normalization),
a deterministic fit-driven strength ladder search (`NamerRoughnessFitter`), the
anchored-inverted dip-depth remap at two consume sites (`CSRoughnessRemap` pre-bakes the
dip for the fit-driven path; `CSSurfacePack` applies it for the Sobel path via
`_RoughnessDipApplied`), and the one-texture binding outcome (residual collapses,
`_BaseResidualMap` left unbound, albedo = vertex color).

The compute math, both dip-remap consume sites, the cross-pool RT ownership rules, and the
lease handling around the reentrant evaluate callback were traced end-to-end and are
correct. The Sobel Gx/Gy coefficients, the `_Strength`-shared frequency-separation chain,
the `ReduceToGlobalMax` stale-tail guards, and the two fit objectives (FitOnlyMaxError vs
MaxError) were all verified against their intent. The material pipeline writes match the
live-preview bindings for the two-texture case.

The phase's defects concentrate at the seams the new default-on path flows through:

1. **The preview misrepresents the headline one-texture output.** When the fit-driven
   extraction collapses the residual, `RecomputePreview` binds the cleaned base at
   `_BaseResidualMap` and draws the vertex-colored split mesh, so the shader computes
   `cleanedBase * _BaseColor * vertexColor` — a base-squared double multiply that does not
   match the saved material (CR-01). The binding line predates 04.1, but this phase routes
   the default `RoughnessExtractStrength = 1` path through it, so what the artist signs
   off on in the viewport is darker than what ships.
2. **Cancellation is silent.** Cancelling the fit progress bar writes un-extracted assets
   with no warning or status anywhere (WR-01).
3. **The fit cache key under-specifies inputs** (occlusion-map identity, base-map content)
   and can serve a stale strength in the persistent editor-window pipeline (WR-02).
4. **Shipped UI copy overpromises**: the slider tooltip and `DefaultRoughnessExtractStrength`
   doc claim strength > 0 enables extraction, while under default settings
   (`DecompositionEnabled = false`) extraction silently no-ops (WR-03).

Verified non-issues (traced, not assumed): `ExtractSobel`'s catch-release/finally split has
no double-release path; `NamerComputePipeline.Process`'s catch block releases the returned
lease exactly once; `ComputeTexturePool.Release` no-ops on foreign targets so cross-pool
release is safe; `RunFrequencySeparation`'s remap `_Strength` is the searched strength
(`ExtractSobel` does not touch it); the cancelled-fit → identity fallback is by documented
design; `NamerSplitResult` is managed arrays (no disposal needed); the two compute shaders
have separate uniform spaces so `_Strength` sharing is not a hazard.

## Narrative Findings (AI reviewer)

### CR-01: Live preview shows base × vertex-color double multiply for the one-texture outcome — preview does not match the saved material

**File:** `Packages/com.graffitientertainment.namer/Editor/UI/NamerEditorWindow.cs:374-381` (with `Packages/com.graffitientertainment.namer/Shaders/NamerSurface.hlsl:104`)

**Classification:** BLOCKER

**Issue:** When the fit-driven extraction collapses the residual (this phase's headline
default path — `RoughnessExtractStrength = 1`, well-fitting base), the saved material is
correctly one-texture: `_BaseResidualMap` is left unbound (white), so
`NamerSurface.hlsl:104` computes `albedo = 1 * _BaseColor.rgb * vertexColor.rgb`.
But `RecomputePreview` binds the cleaned base map into `_BaseResidualMap` whenever
`_decompOutput.Residual != null`:

```csharp
if (_decompOutput != null && _decompOutput.Residual != null)
{
    _namerMaterial.SetTexture(BaseResidualMapId, _decompOutput.Residual);
    _namerMaterial.SetFloat(ResidualStrengthId, _decompOutput.ResidualStrength);
}
else if (previewBaseMap != null)
{
    _namerMaterial.SetTexture(BaseResidualMapId, previewBaseMap);   // line 380
}
```

The `else` branch fires when decomposition is off or produced no residual — exactly the
collapsed-residual case — and the preview then draws `_previewSplitMesh`
(`NamerEditorWindow.cs:772-783`), whose mesh colors carry the fitted vertex-color scale.
The shader multiplies `previewBaseMap * _BaseColor * vertexColor`, i.e. the base is
applied twice. Result: the live preview (which is what `NamerAfterPanelState.PreferGenerated`
shows after any slider tweak) renders noticeably darker than the generated `.mat` does in
the scene. The binding line predates 04.1, but this phase makes the collapsed-residual path
the default outcome, newly exposing it.

**Fix:** When the residual is null/white-equivalent, leave `_BaseResidualMap` unbound so the
preview shader matches the saved material:

```csharp
if (_decompOutput != null && _decompOutput.Residual != null)
{
    _namerMaterial.SetTexture(BaseResidualMapId, _decompOutput.Residual);
    _namerMaterial.SetFloat(ResidualStrengthId, _decompOutput.ResidualStrength);
}
else
{
    // One-texture outcome: residual collapsed. Match the saved material — leave
    // _BaseResidualMap unbound (white) so albedo = _BaseColor * vertexColor.
    _namerMaterial.SetTexture(BaseResidualMapId, null);
}
```

If the pre-decomposition "before" pane still needs the raw base, bind it on a separate
material instance rather than reusing `_namerMaterial`.

## Warnings

### WR-01: Cancelling the fit silently writes un-extracted assets; cancelable progress bar also runs during debounced preview recomputes

**File:** `Packages/com.graffitientertainment.namer/Editor/Pipeline/NamerProcessor.cs:174`; `Packages/com.graffitientertainment.namer/Editor/Bake/NamerRoughnessFitter.cs:85-95`; `Packages/com.graffitientertainment.namer/Editor/Pipeline/NamerRoughnessPipeline.cs:371-375`

**Issue:** `NamerProcessor.RunPipeline` calls
`pipeline.Process(inspection, evaluate, null, settings.ErrorThreshold)` — `shouldCancel`
is null, so `NamerRoughnessFitter.Fit` falls back to `EditorUtility.DisplayCancelableProgressBar`.
Cancelling returns `FitResult.Cancelled`, and `NamerRoughnessPipeline.ExtractFitDriven`
returns an empty result (`ExtractedRoughness = null`, `Cancelled = true`), after which
`NamerComputePipeline.Process` takes the identity path and **still writes all output
assets** (base/surface PNGs, material, mesh) with no extraction applied. There is no
warning, log, or status surfaced anywhere — the user believes they got the feature but the
roughness dip is silently absent. Secondary issues in the same code: (a) the
`debounced-preview` recompute path also calls `RunPipeline` with a null cancel delegate, so
an interactive cancelable progress bar can pop up on slider drags; (b) `Fit`'s
`finally { EditorUtility.ClearProgressBar(); }` runs even when `shouldCancel` was supplied
(non-interactive callers like tests/batch), clearing whatever progress bar the host had
showing.

**Fix:** Propagate cancellation status out of `Process` (e.g. a `bool cancelled` out-param
or a status field on the result), and in `NamerProcessor` either abort the write phase or
emit `Debug.LogWarning("NAMER: roughness fit cancelled — assets written WITHOUT roughness
extraction.")`. Pass a non-interactive `shouldCancel` (returning false) for preview
recomputes, and only touch the progress bar in the branch that displayed it.

### WR-02: Fit cache key omits occlusion-map identity and base-map content — stale strength reuse

**File:** `Packages/com.graffitientertainment.namer/Editor/Pipeline/NamerRoughnessPipeline.cs:77-78, 613-621`

**Issue:** `MakeFitKey` builds the cache key from
`(meshId, baseMapId, aoStrength, aoContrast, aoBlurRadius, aoUnmultiplyStrength, estimator,
w, h, maxErrorThreshold)`. Two inputs to the extracted roughness are missing: (a) the
**occlusion map** — AO participates in `CSNormalize`'s un-multiply of the base that feeds
the Sobel estimator, so swapping `_OcclusionMap` on the source material reuses the cached
strength computed against the old AO; (b) **base-map content** is keyed only by instance ID
(`baseMapId`), so re-importing/rebaking a changed texture into the same `Texture2D` instance
keeps the stale entry. The window holds the pipeline instance for the editor session
(`_roughnessPipeline`), so both staleness modes are reachable without a domain reload.

**Fix:** Add the occlusion map's identity (instance ID, or better, `AssetDatabase` GUID +
file hash when available) to `MakeFitKey`, and include a cheap content stamp for the base
map (e.g. GUID + last-write timestamp). At minimum, document the invalidation contract and
clear the cache when `SourceInspector` detects an occlusion map on the material.

### WR-03: Shipped tooltip/doc claim extraction is enabled by strength > 0 — it silently no-ops under default settings

**File:** `Packages/com.graffitientertainment.namer/Editor/UI/NamerEditorWindow.cs:845-852`; `Packages/com.graffitientertainment.namer/Editor/NamerEditorConstants.cs:44-49`

**Issue:** The roughness slider tooltip states that any value > 0 "ENABLES the auto strength
search", and the `DefaultRoughnessExtractStrength = 1f` doc comment says extraction "runs
automatically when no authored [roughness] map" is present. In reality, extraction only
runs when the pipeline is in fit-driven mode, which requires decomposition to have produced
a bake source mesh + residual — with the shipped defaults (`DecompositionEnabled = false`
in `NamerProcessorSettings`), a user who raises the strength gets the scalar identity path
with zero feedback. The UI/spec claims and the runtime gating disagree; the fit readout
("`picked` N / `passed`/`failed`") is also only drawn on the fit-driven branch, so there is
no signal at all on the silent path.

**Fix:** Either (a) correct the copy — tooltip: "Strength > 0 extracts roughness when
NAMER decomposition is enabled (fit-driven); otherwise the scalar roughness is used", and
fix the constants doc to match; or (b) surface a HelpBox on the Sobel/fit-driven panel when
`RoughnessExtractStrength > 0 && !fitDriven` saying extraction is inactive until
decomposition runs. Option (a) is the minimal honest fix.

### WR-04: `AssetDatabase.SaveAssets()` global flush inside the in-place mesh overwrite path

**File:** `Packages/com.graffitientertainment.namer/Editor/Generation/AssetGenerator.cs:478`

**Issue:** `WriteMeshAsset`'s in-place branch (existing mesh, `existing.Clear(false)` +
`ApplySplitStreams`) ends with `AssetDatabase.SaveAssets()`. That call serializes **every**
dirty asset in the project to disk — including unrelated in-progress user edits — during a
NAMER process run. It directly contradicts the adjacent `WriteMaterial` discipline (its
comment explicitly avoids `SaveAssets` to prevent flushing unrelated dirty assets) and the
project's asset-safety constraint ("source assets must never be modified"). A user with
unsaved scene/asset changes gets them force-committed as a side effect of processing.

**Fix:** Drop the `AssetDatabase.SaveAssets()` call; use
`EditorUtility.SetDirty(existingMesh)` followed by `AssetDatabase.SaveAssetIfDirty(existingMesh)`
(saves only the mesh), matching `WriteMaterial`'s pattern. The call appears in the
`git diff f257f80a^..HEAD` hunk for this phase, so it is new in 04.1, not pre-existing.

### IN-04: `StrengthLadder` exposed as a publicly mutable `float[]`

**File:** `Packages/com.graffitientertainment.namer/Editor/Bake/NamerRoughnessFitter.cs:59`

**Issue:** `public static readonly float[] StrengthLadder = { ... }` — `readonly` on an
array only protects the reference; any caller can sort/mutate it, corrupting the
deterministic ascending ladder search for every subsequent fit in the session.

**Fix:** Expose `IReadOnlyList<float>` (or a `ReadOnlyCollection`/`ImmutableArray`) and keep
the raw array private.

### IN-05: Vacuous test assertions pass even with zero extraction

**File:** `Packages/com.graffitientertainment.namer/Tests/Editor/NamerRoughnessFitTests.cs:132-139, 353-355`; `Packages/com.graffitientertainment.namer/Tests/Editor/NamerEditorWindowSmokeTests.cs:74-75`

**Issue:** (a) `FitDriven_DefaultOn` asserts `ReadPngPixel32(...).a & 0x3F > 0` — but
scalar roughness alone (no dip) quantizes to ~63, so the assertion passes even if the
extraction never ran; (b) `FitDriven_BakedResponse_ResidualCollapses`'s
`Assert.Greater(maxBits, 0)` has the same property; (c) the smoke test asserts
`Assert.AreEqual(9, Mathf.Max(0, 10 - 1))` — pure arithmetic on constants, cannot fail and
verifies nothing about the code under test.

**Fix:** (a)/(b): strengthen to assert a *dip* — e.g. decoded roughness at a known
high-edge texel is strictly below the scalar anchor, or
`packedAlpha < quantize(scalarRoughness)`; (c) replace with an assertion on actual behavior
(e.g. the toolbar selection actually cycles 0..10) or delete it.

### IN-06: CannotDecompose probe yields FitOnlyMaxError = 0 — ladder vacuously passes at strength 0 and is cached as a passed fit

**File:** `Packages/com.graffitientertainment.namer/Editor/Pipeline/NamerProcessor.cs:524-550` (with `NamerDecompPipeline.cs:232`)

**Issue:** When the residual-generation probe returns `CannotDecompose` (zero UV coverage,
e.g. tiling-UV meshes), `EvaluateRefitMaxError` returns 0, the ladder's first rung (0)
passes `0 <= threshold`, and the fit is cached as a **passed** fit with strength 0 — the
window readout then reports "picked 0" as if a real fit occurred. Defensible (no objective
exists for an undecomposable mesh), but the "passed" cache entry plus a normal-looking
readout masks that extraction cannot happen for this mesh at all.

**Fix:** Consider treating a `CannotDecompose` probe as a distinct fit outcome (e.g.
`Supported = false`) and showing "extraction unavailable (mesh not decomposable)" in the
readout, rather than caching a vacuous pass.
