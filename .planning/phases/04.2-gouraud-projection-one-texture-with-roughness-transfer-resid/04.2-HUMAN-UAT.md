## Gaps (round 1 record — GAP-1 and GAP-3 closed, UAT-confirmed round 2; GAP-2 superseded by GAP-4)

### GAP-1: Removed Detail dip produces shiny edges and an inert dip-depth slider

- **Symptom (user, round 1):** one-texture output gets shiny/glossy edges; Roughness Dip Depth slider has no visible effect when moved in the Removed Detail dip source. Sobel Edge @ 0.352 removes the shine (fallback works, default path does not).
- **Root-cause hypothesis (code-verified wiring, fix design belongs to gap planning):** the transfer dip is baked at full adoption — `saturate(scalar - strength * luma/p90)` with pack factor forced to 1 (NamerComputePipeline.cs:173-179, dipApplied=true). Where luma/p90 >> scalar/strength (the projection-error texels: UV seams, triangle boundaries, bright baked speckle) the remap saturates to roughness 0 at ANY slider value, while luma~0 regions never move — the slider's dynamic range is consumed by saturation. The Sobel path instead applies the slider at pack time (CSSurfacePack) and does not fire at projection-error locations, hence no shine there.
- **Acceptance:** default Removed Detail one-texture output shows no shiny edges on the Neo asset; the dip-depth slider produces a visible, monotonic change in gloss variation across its range; Sobel Edge remains available as fallback.
- **Candidate directions (planner/research to decide):** clamp or soft-clip luma/p90; robust percentile normalization (e.g. normalize by a higher percentile or by scalar-relative depth); mask UV-seam/triangle-edge projection error out of the transfer source.

### GAP-2: Preview initial framing must fit each pane's object in screen space (10-20 px margin)

### GAP-3: Close open warnings — code-review Warnings + Metal heatmap translator warning (user-directed)

- **WR-01 (review)** `NamerDecompPipeline.cs:329` (with 398/440): residual ladder resamples to square targets clamped by width only — non-square bases get aspect-distorted residuals, geometrically inconsistent with the full-res aspect-correct Gouraud projection. Fix the resample to respect source aspect.
- **WR-02 (review)** `NamerEditorWindow.cs:600-614`: preview's projection branch consumes `ctx.Decomp` without the CR-03 `CannotDecompose` check `NamerProcessor.cs:210-223` applies — tiling-UV selections preview a decomposition Process will not write. Mirror the guard.
- **WR-03 (review)** `NamerEditorWindow.cs:571`: `ReleaseDecompPreview` nulls `_projectionContext` without disposing `Decomp`; a thrown `Process` (post-`projection.Run`) leaks the pool-leased residual RT across debounced recomputes. One line: dispose `Decomp` (idempotent) before nulling.
- **Shader warning (user-reported, live editor, metal):** `use of potentially uninitialized variable (NAMER_DECOMP_HEATMAP) at kernel CSErrorHeatmap at NAMERDecomp.hlsl(36)`. Root cause: the viridis ramp `NAMER_DECOMP_HEATMAP` (NAMERDecomp.hlsl:23-49) is a chain of early returns; after HLSL->MSL translation the Metal frontend restructures early returns into predicated assignment and emits a false-positive uninitialized-use on the function result (line 36 = first early return). Source math is provably total. Fix: restructure to a single exit point (ternary/select chain preserving the exact piecewise-lerp math); the shared include also covers the `NamerDebugView.shader:143` consumer.
- **Acceptance:** zero of the above warnings in the live editor (console + shader compilation) after the fixes; full EditMode suite green; review Warnings recorded as resolved.
- **Out of scope:** the three review Infos (IN-01 duplicate summary doc, IN-02 WaitForCompletion flags, IN-03 dead `_Verts` upload) unless the user opts them in; 04.1's four Info leftovers keep their recorded disposition.

## Gaps (round 2 — GAP-4 closed at machine level by 04.2-09 + the WR-04 pin; UAT round 3 pending)

### GAP-4: Preview panes must anchor the models toward the center divider with visible pane bounds

- **Symptom (user, round 2, verbatim):** "each frame window is too large? Probably need a outline to tell, as the models are still far apart from each other in default, and the zoom they start to overlap each other, they should be two side by side windows but when scaling the outer window should scale so that the models change the gap between windows, maybe left is right aligned and right is left aligned with 10 pixel left/righ margins?"
- **Three defects:** (a) default framing still leaves a large empty middle — the 04.2-07 fix centers each object in its pane, so the visual gap between models is roughly a pane width minus object width; (b) zooming in past the fit makes each object larger than its pane half and the two objects visually overlap across the divider (nothing constrains them to their panes); (c) no visible pane outline/divider, so the user cannot see the window bounds the fit is targeting.
- **Desired (user spec):** behave as two true side-by-side windows — the LEFT model right-aligned in the left pane, the RIGHT model left-aligned in the right pane, with 10 px left/right margins, so the models hug the center divider with a minimal gap; zoom scales each model outward from the divider (growing away from it, never across it — clipping at the OUTER window edges is expected window behavior); a visible pane outline marks the window bounds.
- **Root-cause notes (code, for planning):** `NamerPreviewRenderer` draws at pane centers `±orthoSize * aspect / 2` computed per Render; the fit uses the rotation-invariant bounding sphere (`extents.magnitude` + MarginPx), which over-approximates the neutral-rotation screen AABB (up to ~1.7x for near-cubic meshes — also makes objects render smaller than a tight width/height fit). Divider-anchored placement needs the object's screen-space half-extent in world units (radius * ppw where ppw = rectHeightPx / (2 * orthoSize)) to position its inner edge at divider ± margin, recomputed per Render so zoom grows objects outward from the divider.
- **Acceptance:** default framing places the two models adjacent at the divider with the pinned inner margins (10 px each side); zooming in grows each model outward from the divider with NO cross-pane overlap at any zoom level; a visible pane outline renders (1 px divider and/or pane borders); framing tests pin the anchored positions; synced orbit and the debug-channel toolbar behave as before.
- **Supersedes:** the 04.2-07 per-pane-centered placement (user round-2 verdict; the MarginPx=15 spherical fit may be retained or replaced by a tight width/height fit at the divider — planner's call, grounded in the code).
