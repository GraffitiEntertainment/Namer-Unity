## Narrative Findings (AI reviewer)

### WR-01: Non-square base maps produce aspect-distorted square residuals

**File:** `Packages/com.graffitientertainment.namer/Editor/Decompose/NamerDecompPipeline.cs:329` (with `:398`, `:440`)
**Issue:** `ChooseResolution` clamps the ladder against `w` only (`Mathf.Min(ResolutionLadder[idx], w)` in the manual branch; the auto search behaves the same), and every path resamples to a square target: `Resample(fullResidual, chosenResolution, chosenResolution)`. For a non-square base (e.g. 2048x1024), the residual EXR is resampled with unequal horizontal/vertical scale factors, so residual texel (u, v) no longer corresponds to base texel (u, v) — the runtime reconstruction multiplies an aspect-correct base against an aspect-distorted quotient, smearing the removed detail along one axis. The phase's new projection path inherits and sharpens this: `projectedOut` stays full-resolution and aspect-correct while the residual written beside it is distorted, so the residual-ON outcome is geometrically inconsistent with the one-texture outcome for the same mesh. Confirmed pre-existing via `git diff a4906b4..HEAD` (this phase only added the projection/mode plumbing), but the file is in scope and the defect is a correctness risk for every non-square base.
**Fix:** Preserve the source aspect in the ladder clamp and the resample. Either clamp by the long edge and scale the short edge:
```csharp
int chosenW = Mathf.Min(ResolutionLadder[idx], Mathf.Max(w, h));
int chosenH = Mathf.Max(1, Mathf.RoundToInt(chosenW * (h / (float)w)));
return Resample(fullResidual, chosenW, chosenH);
```
or resolve `chosenW`/`chosenH` independently against the ladder per axis. The `Stats.ChosenResolution` reporting (square assumption) should follow whatever convention is chosen.

### WR-02: Preview shows a decomposed split mesh for CannotDecompose selections where Process writes the Phase-3 shape

**File:** `Packages/com.graffitientertainment.namer/Editor/UI/NamerEditorWindow.cs:600-614`
**Issue:** `RunDecompPreview`'s projection branch consumes `ctx.Decomp` unconditionally and builds `_previewSplitMesh` from `ctx.Split`/`ctx.Colors`. `NamerProcessor.Process` deliberately checks `ctx.Decomp.Stats.CannotDecompose` (NamerProcessor.cs:210-223) and leaves `decomp` null so the non-decomposed Phase-3 shape is generated with a UV-coverage warning (CR-03). For a zero-coverage selection (tiling/out-of-range UVs) with decomposition enabled and Dip Source = Removed Detail, the window's after pane renders the split mesh with fitted vertex colors and an unbound residual slot, while Process actually writes a Phase-3 material — exactly the preview-must-not-promise-what-Process-will-not-deliver class the window's own CR-01 mirror (NamerEditorWindow.cs:352-356) exists to enforce. The CR-03 fallback was added to the processor this phase but not mirrored into the new preview branch.
**Fix:** Mirror the processor's check at the top of the projection branch:
```csharp
NamerProjectionContext ctx = _projectionContext;
if (ctx.Decomp != null && ctx.Decomp.Stats.CannotDecompose)
{
    // CR-03 mirror: Process generates the Phase-3 shape here — preview must match.
    _decompStats = ctx.Decomp.Stats;
    return;
}
_decompOutput = ctx.Decomp;
_decompStats = ctx.Decomp != null ? ctx.Decomp.Stats : null;
```
(Keeping `_decompStats` populated lets DrawDecompStats still show the honest 0% coverage numbers.)

### WR-03: Leaked pool-live residual when Process throws after the projection ran (window error path)

**File:** `Packages/com.graffitientertainment.namer/Editor/UI/NamerEditorWindow.cs:571` (context lifecycle at `:367-376`)
**Issue:** `RecomputePreview` stores the context in `_projectionContext` (line 372) before calling `_pipeline.Process(inspection, _projectionContext)` (line 376). If `Process` throws after `projection.Run` succeeded — e.g. `ExtractTransferRoughness`'s removed-luma p90 readback failure or a surface-pack dispatch failure — `RunDecompPreview` (line 386) never executes, so `_decompOutput` stays null while `_projectionContext.Decomp` holds a residual RT leased from the persistent `_decompPipeline`'s pool. `ReleaseDecompPreview` then drops the reference at line 571 (`_projectionContext = null;`) without disposing `Decomp`: the RT remains in the pool's live set indefinitely, never returns to the reuse stack, and every subsequent failed recompute leaks another one (the window recomputes are debounced control-driven, so a persistent failure accumulates live RTs across a session). This is the same accumulation class the phase's WR-03 catch-block releases were introduced to prevent for the compute pool; the decomp-pool lease reachable through the new context field was missed. (`NamerProcessor` is not affected: its per-material `finally` disposes the whole decomp pipeline, whose pool teardown destroys live targets.)
**Fix:** Dispose the context's output before nulling — `NamerDecompOutput.Dispose` is idempotent (guarded by `_disposed`), so the happy path where `_decompOutput == ctx.Decomp` (already disposed above) is safe:
```csharp
_projectionContext?.Decomp?.Dispose();
_projectionContext = null;
```
