# Phase 04.3: Adaptive residual resolution via percentile coverage - Context

**Gathered:** 2026-09-22
**Status:** Ready for planning

<domain>
## Phase Boundary

Replace the strict max-error gate in the residual-resolution search with a percentile coverage gate: pick the lowest rung of the existing {2048, 1024, 512, 256, 128} down/up round-trip ladder where the user-chosen fraction of texels (default 99%) stays within the per-texel color tolerance. Also raise the error-threshold slider's max from 0.10 to a higher bound so the two new knobs can actually reach small rungs on noisy sources.

This affects the **residual-ON override path only** (Write Residual checked). The one-texture default path (residual OFF) and its single-material output are untouched.

**Deferred (not this phase):** LOD-based texture tiers (residual off at distance, no-texture smallest LOD). Shelved pending the Ultimate LOD System decision — NAMER will not depend on a third-party LOD generator for now. See Deferred Ideas.

</domain>

<decisions>
## Implementation Decisions

### Gate semantics
- **D-01:** The resolution search's stop condition becomes a **percentile coverage gate** — a rung passes when ≥ the coverage target's fraction of texels have per-texel error ≤ the tolerance. The current strict `evalMaxError > errorThreshold` break at `NamerDecompPipeline.cs:493` is replaced. The walk itself (largest→smallest, skip rungs ≥ source long edge, keep previous passing rung) is unchanged (D-16 lineage).
- **D-02:** **Pure percentile gate** — the worst (1 − target) tail of texels is ignored by the gate. No secondary absolute max-error cap. `MaxError` remains in the stats readout so outlier texels stay visible (honest-reporting precedent from 04.2).
- **D-03:** The per-texel error statistic is the same one the heatmap/error kernels already produce; coverage is a **new reduction statistic** (fraction of texels with error ≤ tolerance), distinct from the existing `Coverage` stat (fraction of texels needing residual). Do not conflate them.

### UI knobs
- **D-04:** **Per-texel tolerance = the existing error-threshold slider.** No new knob for tolerance; moving it already moves achieved coverage. The slider's persisted value (`NamerProcessorSettings.ErrorThreshold`) feeds the gate directly.
- **D-05:** **Coverage target = a new float slider, range 0.90–1.00, default 0.99**, placed beside the error-threshold slider, persisted in `NamerProcessorSettings` like every other control. The two sliders are orthogonal axes: "how wrong is wrong" vs "how much of the image may be wrong".
- **D-06:** **Error-threshold slider max raised from 0.10 to 0.25** (`NamerEditorWindow.cs:1676` hard-codes `0f, 0.10f` today). Default (0.02) unchanged.

### Reporting & fallback
- **D-07:** Stats block (D-09 lineage) gains an **achieved-coverage readout at the chosen rung** (e.g. "coverage 99.4% @ 512") alongside the existing chosen-resolution line.
- **D-08:** **No-rung-passes fallback keeps its current shape** — fall back to the full source long edge and report the shortfall honestly in stats; do not force a smaller rung with a warning.

### Claude's Discretion
- Exact slider step for the coverage slider (0.005 suggested) — planner's call.
- The 0.25 max in D-06 is a reasoned pick, not user-locked — planner may propose a different bound with justification.
- Internal naming of the new coverage statistic and how the compute reduction reports it — planner's call.

### Folded Todos
None folded.

</decisions>

## Existing Code Insights

### Reusable Assets
- `EvaluateResolution` (downsample → upsample round-trip per rung) — already computes per-rung error stats; the phase changes only what statistic gates the walk
- Heatmap/error/coverage compute reductions (`_Threshold`, `_MaxObservedErr` uniform wiring at `NamerDecompPipeline.cs:300-301`) — the per-texel error already exists on GPU; coverage-within-tolerance is an additional reduction, not a new kernel family
- `NamerProcessorSettings` + `NamerEditorWindow` slider wiring — the D-05 coverage slider copies the D-15 threshold slider's persistence pattern exactly

### Established Patterns
- Ladder rungs clamp to the source long edge; rungs ≥ long edge are skipped (D-16)
- Manual override (D-17 popup) bypasses the search entirely — percentile gate changes nothing there
- Stats block reports honest numbers even when gates fail (04.2 precedent)

### Integration Points
- `ChooseResolution` signature gains the coverage target (or reads it from a stats struct) — callers in `NamerDecompPipeline.cs:391`
- Stats UI reads the new achieved-coverage field from `NamerDecompErrorStats`

<specifics>
## Specific Ideas

- User observation driving the phase: "99%+ actually looks like it's often good at 512x512" — the coverage gate should routinely land on small rungs for typical character textures; if it always picks 2048, the tolerance semantics are wrong.
- User framing of the knobs: "the error tolerance slider already changes the 99%–100%" — tolerance and coverage were always two axes of one gate; the UI now says so explicitly.

</specifics>
