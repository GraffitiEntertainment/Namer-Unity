within-threshold flag into `_CoverageStat.r` only for covered texels (0 for uncovered, every
texel written), and `EvaluateResolution`'s normalization

`BuildStats` and the documented D-01 semantics. `AchievedCoverage` is populated on all four

D-07. All three production `GenerateResidual` call sites thread the setting; both window

fixture tests were verified analytically: the 4x4 white-block tail survives despike
(`ResidualSpikeFactor` is 4.0, block/gray quotient ratio is 2.0), the failing-texel budget
(~36 of 65536) sits far under the 1% target margin, and the 1.0-target test has genuine
failing texels at rung 128 so both assertions discriminate.

describes behavior the clamp does not actually deliver, a public field default (`0f`) that

## Narrative Findings (AI reviewer)

### Warnings

### WR-01: Percentile gate at target <= 0 picks the SMALLEST rung — comment claims the opposite

**File:** `Packages/com.graffitientertainment.namer/Editor/Decompose/NamerDecompPipeline.cs:493-496` (comment) and `:527-533` (loop)
**Issue:** The clamp comment says: *"a programmatic 0 / negative / >1 target degrades deterministically (0 -> every rung fails -> the long-edge fallback) instead of mis-gating (T-04.3-01)"*. That is backwards for the 0 case. With `target = 0`, the pass condition `evalCoverage < target` (`coverage < 0`) is never true (coverage >= 0 always), so **every rung passes** and `chosen` ends at the *smallest* ladder rung (128) — maximum downsampling, i.e. exactly the mis-gating the clamp was added to prevent. Only the `> 1` clamp case produces the documented long-edge fallback (every rung fails). The UI slider floor is 0.90, but the value reaches this code unclamped from `NamerProcessorSettings.CoverageTarget` (see IN-03) and from `NamerProjectionContext.CoverageTarget` (see WR-02).
**Fix:** Either make the degenerate case honest and fix the comment, or special-case it:

```csharp
float target = Mathf.Clamp(coverageTarget, 0f, 1f);
// A target of 0 would pass every rung (coverage >= 0 is always true) and land on the
// SMALLEST rung. Treat "no meaningful target" as "gate disabled -> keep full res".
if (target <= 0f)
{
    return Mathf.Max(w, h);
}
```
At minimum, correct the comment so the documented degenerate behavior matches the code.

### WR-02: `NamerProjectionContext.CoverageTarget` defaults to 0f — silent smallest-rung trap

**File:** `Packages/com.graffitientertainment.namer/Editor/Pipeline/NamerComputePipeline.cs:597`
**Issue:** `public float CoverageTarget;` gets the C# field default `0f`. The field exists precisely so `Run` can thread it into `GenerateResidual` (that is how `NamerProcessor.CreateProjectionContext` uses it). Any hand-built context that follows that documented pattern without setting the field — the established mirror pattern in `NamerProjectionAcceptanceTests.BuildProjectionContext` (:398) and `NamerRoughnessFitTests.BuildProjectionContext` (:295) already hand-build contexts — gates at 0 and, per WR-01, silently collapses the residual to the smallest ladder rung. `GenerateResidual`'s default parameter only protects direct calls, not the context field. Production is safe today only because `CreateProjectionContext` always assigns it.
**Fix:**

```csharp
/// <summary>Coverage target passed to <c>GenerateResidual</c> (D-05 percentile gate).</summary>
public float CoverageTarget = NamerEditorConstants.DefaultCoverageTarget;
```

### IN-02: Gate statistic is quantized through the float16 reduce chain

**File:** `Packages/com.graffitientertainment.namer/Editor/Decompose/NamerDecompPipeline.cs:577-579`
**Issue:** The percentile fraction the gate compares (`covStats.MeanErr / stats.CoverageFraction`) is reduced through the `R16G16B16A16_SFloat` ping-pong targets (`avgA`/`avgB`), so it carries ~2^-11 (~5e-4) relative half-float error — the final RGBAFloat readback is exact but the intermediates are not. A rung whose true coverage is within ~0.05-0.1% of the 0.99 target can pass/fail non-deterministically with respect to the exact rational value, shifting the chosen rung by one step. The previous max-error gate had the same quantization class, and the adaptive search is a heuristic, so impact is bounded — but the gate boundary now sits exactly on this noise.
**Fix:** If rung-boundary determinism matters, reduce the gate statistic through a `R32G32B32A32_SFloat` chain (or accept and document the tolerance).

### IN-03: `CoverageTarget` pref is unclamped relative to the UI range

**File:** `Packages/com.graffitientertainment.namer/Editor/Settings/NamerProcessorSettings.cs:139-143`; `Packages/com.graffitientertainment.namer/Editor/UI/NamerEditorWindow.cs:1691-1707`
**Issue:** The slider writes only [0.90, 1.00], but the getter returns whatever the pref holds. `ChooseResolution` clamps to [0, 1] — so an out-of-band pref of e.g. 0.5 gates Process at 0.5 while the window slider *displays* the clamped 0.90 (`EditorGUILayout.Slider` clamps its displayed value), producing a silent preview/Process disagreement until the user touches the slider.
**Fix:** Clamp on read (`Mathf.Clamp(EditorPrefs.GetFloat(...), 0.90f, 1f)`) or clamp `_coverageTarget` when loading it in `RebuildInspection` so the window and Process always agree.
