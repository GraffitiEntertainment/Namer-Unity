# Phase 5.1: Reference-fitted URP post-processing look - Research

**Researched:** 2026-09-24
**Domain:** URP 17.0.4 post-processing Volume API + deterministic CPU color-grade fitting (Unity 6000.0.82f1 editor package)
**Confidence:** HIGH

## Summary

The entire URP post stack this phase targets was read from the **exact installed package source** (`Library/PackageCache/com.unity.render-pipelines.universal@c7abd84d7030` = URP 17.0.4, `com.unity.render-pipelines.core@f663854f0ceb`), not from docs or training data. Every parameter range, the grading operator order, the CPU→shader uniform mappings, and the VolumeProfile asset-creation pattern are verified with file:line citations below. The single most load-bearing discovery: **this project's active URP asset (`Assets/NAMER/NamerSmokeURP.asset`, wired via GraphicsSettings guid `d1494954c81d842e0ae26e6a5f532aae`) runs `m_ColorGradingMode: 0` = LowDynamicRange grading — which is also the C# default for new URP assets** (`UniversalRenderPipelineAsset.cs:582`). That selects a *specific* runtime pipeline the preview must match: ACES tonemaps at uber-pass time, and white balance / contrast / saturation / curves all apply **post-tonemap** through the linear internal LUT — not the pre-tonemap ACES-space path described in most URP documentation (that is the HighDynamicRange grading mode).

The fit is a classical estimator suite (von Kries white balance, mean-luma EV ratio, percentile-spread contrast, chroma-ratio saturation, histogram-specification curves) — no library exists or is needed; the phase forbids new dependencies and the deterministic serial-CPU precedent (`NamerStyleExtractor`, Phase 05 decision) already establishes the code shape. One genuine piece of reuse exists: `ColorUtils.ColorBalanceToLMSCoeffs(temperature, tint)` is **public C# in core** (`Runtime/Utilities/ColorUtils.cs:67`) and is the exact function URP's LUT pass calls — the fit's temperature/tint inversion should evaluate candidates through it, eliminating port-drift for white balance. The ACES tonemap and LogC curves have no C# counterpart and must be ported once into a shared CPU math class, pinned by golden-value tests against the HLSL.

**Primary recommendation:** implement the fit + in-shader preview against the **LDR grading path** (post-tonemap linear LUT, LogC contrast pivot `0.4135884`, Rec.709 saturation luma pivot), generate the VolumeProfile as `CreateAsset` + `AddObjectToAsset` per component (Unity's own pattern), and pin the estimator math with synthetic-pair tests in the `Bake_IsDeterministic` bar.

### Pattern 1: The URP 17.0.4 LDR grading pipeline (the preview's contract)

The project's active URP asset is `m_ColorGradingMode: 0` = **LowDynamicRange** grading [VERIFIED: `Assets/NAMER/NamerSmokeURP.asset` line 79 + GraphicsSettings guid + `UniversalRenderPipelineAsset.cs:582` shows this is also the C# default for new assets]. With a Volume whose Tonemapping = ACES, the runtime operator order is [VERIFIED: `UberPost.shader` via `Common.hlsl:113-159` + `PostProcessPass.cs:1525-1560` + `LutBuilderLdr.shader:41-141`]:

```
1. Bloom prefilter:      brightness = Max3(r,g,b) on LINEAR HDR color,
                         threshold = GammaToLinearSpace(thresholdUI), knee = threshold*0.5
                         (Bloom.shader:96-100, PostProcessPass.cs:1355-1361)
                         — PRE-postExposure: EV never affects what blooms
2. Uber:                 c *= 2^postExposure                     (PostProcessPass.cs:1534)
3. Uber: ApplyTonemap:   aces = unity_to_ACES(c); c = saturate(AcesTonemap(aces))
4. Uber: internal LUT sample (baked by LutBuilderLdr):
     4a. White balance:  LMS = LIN_2_LMS * c; LMS *= ColorBalance(t°,tint); c = LMS_2_LIN
     4b. Contrast:       logC = LinearToLogC(c);
                         logC = (logC − 0.4135884)·z + 0.4135884;   // z = contrast/100 + 1
                         c = LogCToLinear(logC)
     4c. colorFilter:    c *= filter (neutral white ⇒ identity — stays neutral per UI-SPEC)
     4d. (split toning / channel mixer / SMH / lift-gamma-gain — all identity/neutral)
     4e. Saturation:     luma = Luminance709(c); c = luma + s·(c − luma)  // s = sat/100 + 1
     4f. YRGB curves:    c += 1/256; master per-channel; c += 1/256; R/G/B curves
                         (NO FastTonemap sandwich on the LDR path; LinearClamp ⇒ x∈[0,1])
     4g. saturate(c)
```

The in-shader preview implements exactly steps 2–4g (deterministic, parameterized by the serialized fit block); bloom preview is approximate (see Open Questions). The fit's statistics are computed in the matching domains: contrast spread in LogC of the post-tonemap source, saturation chroma on post-tonemap linear, curves' histogram specification over post-tonemap linear [0,1] — the same domain the reference's sRGB-decoded values live in (references are display-referred; sRGB-decode lands them directly in the LDR LUT's input domain — a genuinely convenient coherence of the LDR path).

**HDR grading mode divergence (documented, not implemented):** if a user's URP asset sets Grading Mode = HighDynamicRange, `LutBuilderHdr.shader:71-187` instead grades PRE-tonemap in ACES spaces (contrast pivots ACEScc via `ACES_to_ACEScc(unity_to_ACES(c))`, saturation pivots `AcesLuminance` = AP1 RGB2Y, curves sit inside a `FastTonemap`/`FastTonemapInvert` sandwich so their x-domain is c/(1+c), and the ACES tonemap is baked into the LogC LUT). The fitted Volume parameters are identical; only the preview/fit math domains differ. v1 targets the LDR path (project asset + URP default); see Open Questions.

### Pattern 2: VolumeProfile generation (Unity's own pattern)

```csharp
// Source: core RP editor code pattern (VolumeProfileUtils.cs:235) + VolumeProfile.cs
var profile = ScriptableObject.CreateInstance<VolumeProfile>();
var tm = profile.Add<Tonemapping>();            // throws if the type already exists
tm.mode.overrideState = true;
tm.mode.value = TonemappingMode.ACES;           // parameter-free: the enum is the whole override

var wb = profile.Add<WhiteBalance>();
wb.temperature.overrideState = true;  wb.temperature.value = fittedTemp;   // [-100,100]
wb.tint.overrideState = true;         wb.tint.value = fittedTint;          // [-100,100]

var ca = profile.Add<ColorAdjustments>();
ca.postExposure.overrideState = true; ca.postExposure.value = fittedEv;    // EV100, unclamped
ca.contrast.overrideState = true;     ca.contrast.value = fittedContrast;  // [-100,100]
ca.saturation.overrideState = true;   ca.saturation.value = fittedSat;     // [-100,100]

var bloom = profile.Add<Bloom>();
bloom.threshold.overrideState = true; bloom.threshold.value = fittedThreshold; // gamma-space, ≥0
bloom.intensity.overrideState = true; bloom.intensity.value =
    NamerEditorConstants.DefaultBloomIntensity;                               // artist knob (1.0)

var curves = profile.Add<ColorCurves>();
curves.master.overrideState = true;
curves.master.value = new TextureCurve(keys, 0f, false, new Vector2(0f, 1f));

AssetDatabase.CreateAsset(profile, volumePath);        // path per AssetGenerator conventions
AssetDatabase.AddObjectToAsset(tm, profile);           // EVERY component — see Pitfall 1
AssetDatabase.AddObjectToAsset(wb, profile);
AssetDatabase.AddObjectToAsset(ca, profile);
AssetDatabase.AddObjectToAsset(bloom, profile);
AssetDatabase.AddObjectToAsset(curves, profile);
AssetDatabase.SaveAssets();
EditorGUIUtility.PingObject(profile);                  // UI-SPEC ping idiom
```

Either satisfies the UI-SPEC table; recommend per-parameter.

`TextureCurve(Keyframe[] keys, float zeroValue, bool loop, in Vector2 bounds)` [VERIFIED: `TextureCurve.cs:74`]; `TextureCurveParameter(value, overrideState)` [VERIFIED: same file]. ### Pattern 3: Fit lifecycle (mirror of Extract)

`NamerStyleExtractor` is the template [VERIFIED: `Editor/Stylize/NamerStyleExtractor.cs`]: explicit action only, result-object shape (success / cancelled / error-texture-name / too-few-refs), fixed named constants for every literal (kPercentile10/90 already exist there), exact sRGB decode constants, serial deterministic accumulation, `ClampToCaps` pre-validation. ### Anti-Patterns to Avoid
- **Writing the Volume with values computed in the wrong domain** — e.g., contrast percentiles on raw linear source instead of post-tonemap LogC; the preview would match the fit but neither would match the scene Volume.
- **Baking post into anything persistent besides the Volume** — the phase premise forbids tone-mapped color in albedo/any saved texture; the post math exists only in the preview shader path and the Volume.
- **Trying to closed-form invert `ColorBalanceToLMSCoeffs`** — it is piecewise and asymmetric (see Pitfall 6); use a fixed-iteration 2D solve.
- **Auto-refit on Process or debounce** — D-01/D-03 lock explicit-only.

## Common Pitfalls

### Pitfall 1: VolumeComponents are sub-assets — `CreateAsset` alone loses them
**What goes wrong:** `VolumeProfile.components` is a `List<VolumeComponent>` of `UnityEngine.Object` references; `AssetDatabase.CreateAsset(profile, path)` serializes the profile but not the `CreateInstance`'d components — they dangle and load back null.
**Why it happens:** `profile.Add<T>()` creates instances at runtime; nothing automatically parents them to the asset file.
**How to avoid:** `AssetDatabase.AddObjectToAsset(component, profile)` for every component before `SaveAssets()` — exactly what Unity's `VolumeProfileUtils.cs:235` and `VolumeComponentListEditor.cs:501` do.
**Warning signs:** generated profile shows empty component list on reimport; "Component already exists" `InvalidOperationException` on re-fit if you `Add` into a loaded stale profile (regenerate a fresh profile instance per fit — D-02 accepts wholesale replacement).

### Pitfall 2: Building the preview against the HDR grading path
**What goes wrong:** most URP documentation describes HDR grading (grading pre-tonemap in ACES spaces). Implement that and the preview silently mismatches this project's scenes, which run `m_ColorGradingMode: 0` (LDR): ACES at uber time, WB/contrast/sat/curves post-tonemap, LogC-space contrast, Rec.709 saturation pivot, no FastTonemap curve sandwich.
**Why it happens:** the mode lives on the URP asset, not the Volume — invisible in the Volume-creation code.
**How to avoid:** implement the LDR chain (Pattern 1) and document the divergence; do not read `Camera.allowHDR` — the relevant switch is the asset's Grading Mode.
**Warning signs:** preview looks more contrasted/desaturated than the same Volume in-scene.

### Pitfall 3: postExposure semantics
**What goes wrong:** treating EV as a display-space multiplier or expecting it to affect bloom.
**What actually happens [VERIFIED: `PostProcessPass.cs:1534`, `Common.hlsl:113-116`, `ColorAdjustments.cs:14-18`]:** the multiplier is `2^EV`, applied in the uber pass AFTER bloom/DOF and immediately BEFORE the LUT sample — in the LDR path that is after the ACES tonemap's input, i.e., EV feeds the tonemap. Fitting EV as a plain post-tonemap mean-luma ratio is biased (the tonemap compresses); a fixed-iteration 1D bisection through the CPU forward chain removes the bias if wanted (discretion — the locked wording is "mean-luma EV ratio").
**Warning signs:** fitted EV systematically undershoots on bright references.

### Pitfall 4: Bloom threshold is gamma-space, brightness is Max3
**What goes wrong:** writing a linear percentile into `threshold.value`, or computing "highlights" with luma.
**What actually happens [VERIFIED: `Bloom.cs:36`, `PostProcessPass.cs:1355`, `Bloom.shader:96-100`]:** the UI value is gamma-space; URP converts via `Mathf.GammaToLinearSpace` at render time and compares against `Max3(r,g,b)` (not luminance) with a hardcoded soft knee `threshold*0.5`. A reference highlight percentile computed in sRGB display space IS the gamma-space value — write it directly, no conversion.
**Warning signs:** bloom firing on midtones (threshold written in linear ≈ smaller).

### Pitfall 5: Contrast pivot and saturation pivot spaces
**What goes wrong:** matching percentile spreads in linear or sRGB.
**What actually happens [VERIFIED: `LutBuilderLdr.shader:50-53,116-118`]:** contrast scales LogC-space deviations around the constant `0.4135884` (`ACEScc_MIDGRAY` reused as the LogC pivot — URP's actual code, not a typo); saturation scales deviations from **Rec.709 luma** in linear. The contrast solve is `z = refSpreadLogC / srcSpreadLogC`, `contrast = (z − 1)·100`, clamped to [−100, 100].
**Warning signs:** contrast fit wildly off on dark-heavy pairs.

### Pitfall 6: White-balance inversion has no closed form
**What goes wrong:** algebraically solving temperature/tint from von Kries LMS gains.
**Why:** `ColorBalanceToLMSCoeffs` is piecewise — `x = 0.31271 − t1·(t1 < 0 ? 0.1 : 0.05)`, `y = StandardIlluminantY(x) + t2·0.05`, `t1 = temp/65`, `t2 = tint/65`, then CAT02-style LMS ratios vs D65 `(0.949237, 1.03542, 1.08728)` [VERIFIED: `ColorUtils.cs:32-82`].
**How to avoid:** fit the target LMS gains von Kries-style (source-mean vs reference-mean chromaticity), then run a small fixed-iteration 2D solve (e.g., nested golden-section or fixed Newton steps over temperature ∈ [−100,100], tint ∈ [−100,100]) minimizing LMS-gain distance — deterministic, pinned by tests. The `±100` UI range corresponds to |t|/65 ≈ 1.54 (the "range ~[−1.5;1.5] works best" comment).
**Warning signs:** solve diverging or clamping at ±100 on mild casts.

### Pitfall 7: Curves domain + quantization
**What goes wrong:** histogram-specifying curves in sRGB or unbounded linear.
**What actually happens [VERIFIED: `LutBuilderLdr.shader:120-138`]:** the LDR path evaluates curves on the linear LUT value with a `1/256` pre-offset for master and again for RGB, LinearClamp (x effectively [0,1]), master applied per-channel (not on luma), RGB applied after master; the curve texture is 128 texels. Histogram specification: build source and reference CDFs over post-tonemap linear [0,1], map `y = Fr⁻¹(Fs(x))`, sample at a fixed key grid, smooth/enforce monotonicity, cap keys (named constant ≤ 16).
**Warning signs:** banding or dead curve regions; keys crowded beyond 128-texel resolution.

### Pitfall 8: Metal unbound-property silent skip (house memory)
Any new shader uniform the preview dispatch touches must be set unconditionally — Unity 6/Metal silently skips on unbound properties. The post-preview uniforms (enable flag, temp/tint coeffs, EV, sat, curve data) are set as a full table on every preview path, exactly like the 05-03 kernel binding discipline. (Fragment-shader floats default to 0 rather than skipping, but the house rule is unconditional binding regardless.)

### Pitfall 9: Exemplar source is a GPU RT — readback, not GetPixels
The palette-mapped stylized output lives in a pool-leased `RenderTexture`. The fit consumes it via the existing readback contract (`NamerComputePipeline.RequestReadback`); determinism tests do NOT ride this path — they pin the estimator math on synthetic CPU arrays (ROADMAP criterion 5, `Bake_IsDeterministic` bar). GPU readback values are machine-stable, not cross-GPU-guaranteed — which is precisely why the tests are synthetic.

### Pitfall 10: Re-fit must not leak old TextureCurves / components
Replacing `curves.master.value` orphans the previous `TextureCurve` sub-asset inside the profile. Since D-02 accepts wholesale regeneration ("hand-tweaks lost"), regenerate the Volume asset fresh (delete-or-overwrite via a new profile instance at the same path per the overwrite-generated opt-in) rather than mutating a loaded profile.

### Estimator sketches (deterministic; domains per Pattern 1)

```csharp
// von Kries: target LMS gains from mean chromaticities (gray-world style anchor)
// srcMean/refMean = mean linear color of stylized source / sRGB-decoded references.
float3 gains = LinearToLms(refMean) / max(LinearToLms(srcMean), kEps);
// then fixed-iteration 2D solve over (temperature, tint):
//   min |ColorBalanceToLMSCoeffs(t, ti) - normalized(gains)|

// Contrast: post-tonemap LogC percentile spread
float z = (refP90LogC - refP10LogC) / max(srcP90LogC - srcP10LogC, kEps);
float contrast = math.clamp((z - 1f) * 100f, -100f, 100f);

// Saturation: mean chroma ratio in the LDR-path domain (post-tonemap linear)
float s = refMeanChroma / max(srcMeanChroma, kEps);
float saturation = math.clamp((s - 1f) * 100f, -100f, 100f);

// EV: locked wording is the mean-luma ratio (optionally refined by 1D bisection)
float ev = math.log2(math.max(refMeanLuma, kEps) / math.max(srcMeanLuma, kEps));

// Bloom threshold: reference highlight percentile IN sRGB display space (gamma-space write)
float bloomThreshold = Percentile(refSrgbMax3, kBloomHighlightPercentile); // e.g. p99 constant
```

Chroma/percentile/luma statistic definitions, percentile picks, and smoothing are discretion — but each must be a named constant and each must state its domain (the estimator comments should say "LogC of post-tonemap linear", etc.).
