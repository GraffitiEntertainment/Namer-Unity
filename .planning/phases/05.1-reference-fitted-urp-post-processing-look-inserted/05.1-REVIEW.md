## Summary

Phase 05.1 adds the reference-fitted URP post-processing look: a CPU fit core
(`NamerStylePostMath` / `NamerStylePostFit`), the fitted-post block on
`NamerStyleProfile`, a VolumeProfile writer (`NamerStyleVolumeWriter`), the Fit
Look lifecycle in the window/inspector/processor, and the in-shader post
preview (`NamerPostPreview.hlsl`, `NAMER.shader`, `NamerPostBloom.shader`,
`NamerPreviewRenderer`).

The math fidelity work is the strongest part of this phase and was verified
against the installed URP 17.0.4 sources rather than taken on faith: the
in-shader chain (post-exposure multiply -> ACES tonemap -> LMS white balance ->
LogC contrast around ACEScc_MIDGRAY -> Rec.709 saturation -> YRGB curves with
the (1/128)/2 half-pixel offsets -> saturate) matches
`UberPost/Common.hlsl` and `LutBuilderLdr.shader` step for step;
`ColorUtils.ColorBalanceToLMSCoeffs` and the z = value/100 + 1 conversions
match `ColorGradingLutPass.cs:175-176`; the bloom threshold conversion and
0.5 knee match `PostProcessPass.cs:1355-1356`. The full-table uniform
discipline (Metal silent-skip law), destination confinement, overwrite gates,
and RT/material cleanup in the bloom chain are all correctly implemented. The
new test suites are genuinely adversarial (golden pins, gate pinning,
EditorPrefs snapshot/restore, monotonicity sweeps).

The defects concentrate in the interactive Fit Look flow, not the math: the
feature's core iteration loop (fit, review, re-fit) breaks on default
settings because the profile is mutated before the Volume write hits the
overwrite gate (CR-01); the fit accepts a zero-mass reference set and writes a
maximal black grade as a "success" (WR-01); the exemplar/base coupling can
silently stylize with the wrong profile or no stylization at all (WR-02); and
one Fit Look failure path is a silent no-op (WR-03). None of the classified
non-regressions from the task context (the three AssetGenerator internal
widening members; the two pre-existing headless-GPU test failures) are
re-flagged here.

## Critical Issues

### CR-01: Second Fit Look always fails on default settings — after the profile has already been mutated

**File:** `Packages/com.graffitientertainment.namer/Editor/UI/NamerStyleProfileEditor.cs:459-474`
**Issue:** `RunFitLook` commits the new fit to the profile first
(`Undo.RecordObject` + `NamerStylePostFit.ApplyToProfile` + `EditorUtility.SetDirty`,
lines 459-461) and only then calls `NamerStyleVolumeWriter.Write` (line 468).
`NamerProcessorSettings.OverwriteGenerated` defaults to `false`, and
`NamerStyleVolumeWriter.Write` runs `AssetGenerator.EnsureWritableTarget(path,
settings.OverwriteGenerated)` (`NamerStyleVolumeWriter.cs:63`) which throws once
the first fit has created `{ProfileName}_Post.asset`. Consequences on default
settings:

1. The FIRST Fit Look succeeds; EVERY subsequent Fit Look throws — the exact
   iteration loop the feature exists for is broken out of the box.
2. Each failed re-fit leaves divergent state: the profile (the declared
   "source of truth") carries the NEW fit while the generated Volume keeps the
   OLD one, and the HelpBox reports "Fit failed: ..." even though the fit
   itself succeeded and was committed.
3. The documented behaviors are contradicted: the button tooltip
   (`NamerStyleProfileEditor.cs:353`) says "Re-fitting replaces the fit and
   overwrites the generated Volume"; `docs/USER_GUIDE.md` (Stylization section)
   says "refitting with another object replaces the scene look" and "Whenever
   Process runs with a fitted profile attached, the companion Volume is
   regenerated so the generated bundle never desyncs from profile truth". The
   Process-time regeneration in `NamerProcessor.cs` (~line 385) hits the same
   gate and degrades to a buried `result.Warnings` entry — so with default
   settings the Volume NEVER follows profile truth after the first write.

`NamerStyleVolumeWriterTests.Write_RefusesWhenOptInOff` pins the writer's gate
semantics (correct in isolation); the defect is the ordering and remediation
in the interactive flow, which no test covers.

**Fix:** Pre-flight the write gate BEFORE mutating the profile, so a refusal
leaves the profile untouched and the ordering cannot diverge:

```csharp
// Before Undo.RecordObject/ApplyToProfile:
NamerProcessorSettings settings = new NamerProcessorSettings();
AssetGenerator.EnsureWritableTarget(
    NamerStyleVolumeWriter.ComposeVolumePath(profile, settings),
    settings.OverwriteGenerated);

Undo.RecordObject(profile, "Fit Look");
NamerStylePostFit.ApplyToProfile(profile, result.Params, result.ExemplarName);
EditorUtility.SetDirty(profile);
VolumeProfile volume = NamerStyleVolumeWriter.Write(profile, settings);
```

Additionally, make the fit's own companion Volume opt-in independent of the
user's generated-asset overwrite toggle (the tooltip/guide promise
refit-overwrite unconditionally), or at minimum roll the profile back inside
the existing `catch` (undo the `Undo.RecordObject` frame) so a failed
re-fit never desyncs profile and Volume.

## Warnings

### WR-01: Fit accepts a zero-mass reference set and writes a maximal black grade as success

**File:** `Packages/com.graffitientertainment.namer/Editor/Stylize/NamerStylePostFit.cs:244-322`
**Issue:** `Fit` never validates `reference.TotalWeight > 0`. A zero total is
reachable through the UI: every reference slot cleared after extraction
(`RunStylePostFit` skips null slots, `NamerEditorWindow.cs:2373-2377`, and
`FitButtonState` only checks `IsExtracted` + exemplar availability), or all
reference weights set to 0 (the weight clamp explicitly allows 0 — see
`Profile_ClampToCaps_TruncatesReferencesAndClampsWeights`). With
`refTotal == 0`: `WeightedPercentile`/`CdfInvert` return 0 everywhere, so
`refSpread == 0` drives `spreadRatio == 0` and `Contrast` rails to -100
(line 279-280); `refLumaMean` floors to epsilon and `PostExposureEv` rails to
-10 (lines 265-267); saturation rails to -100; every histogram-specification
curve value collapses to 0 (lines 312-316) — a maximal black grade written as
a successful fit, with the Volume regenerated to match. No error, no refusal.
**Fix:** Guard at the top of `Fit` (and surface it in `RunStylePostFit` as a
named failure like the isReadable path):

```csharp
if (reference.TotalWeight <= 0.0)
{
    throw new InvalidOperationException(
        "The profile's references carry no weight (all slots empty or all weights 0) — no post look can be fitted.");
}
```

Mirror the guard as a `FitButtonState` reason (references with positive total
mass) so the button explains itself instead of failing on click.

### WR-02: Fit Look can stylize the exemplar base with the wrong profile — or none — and fit onto the inspected profile

**File:** `Packages/com.graffitientertainment.namer/Editor/UI/NamerStyleProfileEditor.cs:389-406` and `Packages/com.graffitientertainment.namer/Editor/UI/NamerEditorWindow.cs:548-550, 2421-2431`
**Issue:** In the standalone (Project window) inspector, `ResolveExemplarWindow`
falls back to the FIRST open Processor window with a loadable source — which
may have a different style profile attached, or none. `RunStylePostFit(profile)`
then (a) reads references/weights from the INSPECTED profile but (b) computes
the stylized base with the WINDOW's attached profile: the stylize lens is
`styleProfile != null && (... || _forceStylizeForFit)` (lines 548-550), so when
the fallback window has no profile attached, `_forceStylizeForFit` is a no-op
and the fit measures the UN-stylized base — the reference grade then absorbs
the missing stylization into the post knobs (wrong decomposition, silently).
When it has a different profile attached, the base is stylized by the wrong
palette. The embedded case is aligned by construction; only the fallback path
diverges, and nothing warns the user.
**Fix:** Pass the inspected profile through to the forced recompute (e.g., an
optional `NamerStyleProfile overrideProfile` on the forced-stylize path that
replaces `ResolveStyleProfile(_settings)` for that one recompute), or restrict
`ResolveExemplarWindow` to windows whose attached profile IS the inspected
profile and extend the locked no-exemplar reason to cover "no window with this
profile attached".

### WR-03: Fit Look silently no-ops when the exemplar window has a source but no processed pipeline

**File:** `Packages/com.graffitientertainment.namer/Editor/UI/NamerEditorWindow.cs:2355-2358` and `Packages/com.graffitientertainment.namer/Editor/UI/NamerStyleProfileEditor.cs:445-450`
**Issue:** `RunStylePostFit` returns `notExtracted: true` when
`!HasLoadableSource || _pipeline == null`. `HasLoadableSource` is only
`_selection != null && PrimaryInspection != null` (line 2330-2333) — `_pipeline`
is created lazily by the debounced preview recompute, so in the window between
loading a source and the first recompute (or after a recompute that never
created a pipeline) the Fit Look button is ENABLED (`FitButtonState` checks
only extraction + exemplar availability, lines 302-317) and the click returns
`NotExtracted == true`, which `RunFitLook` treats as "the next repaint
re-evaluates FitButtonState and renders the active locked reason" — but that
reason is null in this state, so the user gets a completely silent no-op. The
`notExtracted` flag is also semantically wrong for this failure (the profile
IS extracted; the window has no processed result).
**Fix:** Split the guard into its own result state (or an `ErrorTextureName`-
style message) that renders a fitError like "the Processor window has no
processed preview yet — wait for the preview or press Process first", and
preferably let the stage-2 `RecomputePreview()` create the pipeline instead of
bailing before it.

### WR-04: Volume writer force-flushes every dirty asset in the project

**File:** `Packages/com.graffitientertainment.namer/Editor/Stylize/NamerStyleVolumeWriter.cs:115`
**Issue:** `Write` calls `AssetDatabase.SaveAssets()` after `CreateAsset` +
five `AddObjectToAsset` calls. `SaveAssets()` flushes EVERY dirty asset in the
project, contradicting the codebase's own established discipline —
`AssetGenerator.cs:491` documents "SaveAssets() flushes every [dirty asset]"
as the reason the main generator avoids it. A Fit Look click (or every Process
with a fitted profile attached, via the `NamerProcessor` hook) can therefore
force-write unrelated user assets the user did not intend to save yet.
**Fix:** Scope the save to the asset just written (Unity 6 API):

```csharp
EditorUtility.SetDirty(volume);
AssetDatabase.SaveAssetIfDirty(volume);
```

(or `AssetDatabase.SaveAssetIfDirty(AssetDatabase.GUIDFromAssetPath(path))`)
so only the Volume and its sub-assets are persisted.

## Info

### IN-01: Fitted bloom threshold of exactly 0 disables the pane bloom but maximally blooms the generated Volume

**File:** `Packages/com.graffitientertainment.namer/Editor/UI/NamerPreviewRenderer.cs:275`
**Issue:** `PostBloomEnabled => _bloomIntensity > 0f && _bloomThresholdLinear > 0f`
treats threshold 0 as the disabled sentinel, but 0 is a legal fitted value
(p95 of a near-black reference; `ClampToCaps` lower-bounds the threshold at 0)
and in URP a threshold of 0 blooms EVERYTHING — so at exactly 0 the After pane
shows no bloom while the runtime Volume blooms maximally. Preview/runtime
divergence at the boundary.
**Fix:** Disable on an explicit negative sentinel (e.g., `SetPostBloom(-1f, 0f)`
from the null/unfitted paths) and let threshold 0 arm the chain, matching URP.

### IN-02: SanitizeCurve clamps keys but never re-sorts out-of-order keys

**File:** `Packages/com.graffitientertainment.namer/Editor/Stylize/NamerStyleProfile.cs:392-414`
**Issue:** `SanitizeCurve` clamps times/values into [0,1] and writes
`curve.keys = keys`, but a hand-edited curve with descending key times
(e.g., 0.8 then 0.2) stays unsorted after clamping — `AnimationCurve`
evaluation with unsorted keys is undefined. Every consumer (curve strip build,
Volume `TextureCurve` build) assumes sorted input.
**Fix:** After the clamp loop, `System.Array.Sort(keys, (a, b) => a.time.CompareTo(b.time));`
before assigning back (dedupe identical times if desired).

### IN-03: Static curve-strip cache is destroyed by one window's OnDisable while other windows may still bind it

**File:** `Packages/com.graffitientertainment.namer/Editor/UI/NamerEditorWindow.cs:165-166, 352-360`
**Issue:** `_postCurveTexture` is `static` (one shared strip) but destroyed in
the per-instance `OnDisable`. With two Processor windows at the post lens,
closing window A destroys the texture window B's preview material still has
bound; B renders against a destroyed texture until its next `ApplyPostLook`
rebuilds the strip. Transient visual corruption in a multi-window edge.
**Fix:** Make the cache per-window (instance field), or key the destroy on
domain reload only (`AssemblyReloadEvents.beforeAssemblyReload`), or re-bind
lazily each `ApplyPostLook` call before dispatch (it already rebuilds when
null — the gap is only the bound-but-destroyed window between disables).

### IN-04: ComposeVolumePath lacks the destination normalization the main generator applies

**File:** `Packages/com.graffitientertainment.namer/Editor/Stylize/NamerStyleVolumeWriter.cs:35`
**Issue:** `ComposeVolumePath` concatenates `settings.Destination + prefix +
...` directly, while `AssetGenerator.ComposeDestinationFolder`
(`AssetGenerator.cs:298-301`) normalizes with `TrimEnd('/', '\\') + "/"`. A
destination persisted without a trailing separator (editable via
EditorPrefs/the settings field) glues the file name onto the folder
("Assets/NamerGen" + "P_Name_Post.asset") and `ValidateComposedPath` then
rejects it with the misleading "Generated path escapes the destination
folder" error. No write escapes Assets (the confinement holds), but the
failure is unactionable.
**Fix:** Apply the same normalization:
`return settings.Destination.TrimEnd('/', '\\') + "/" + prefix + ...`.
