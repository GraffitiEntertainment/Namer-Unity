# Phase 5.2: Standalone post-look asset - Context

**Gathered:** 2026-09-27
**Status:** Ready for planning
**Source:** In-session design discussion (context-gate option "Use this session"); no separate discuss-phase run

<domain>
## Phase Boundary

Move the Phase 5.1 reference-fitted post look out of the NAMER Processor window and off the `NamerStyleProfile` into a standalone `NamerPostLook` ScriptableObject. The asset is the home of the post look: its own reference-image list, the Fit action (fed by the Processor window's live stylized render), hand-tweakable fitted parameters in the main Inspector, and per-asset generated URP Volume profiles. ToneMatch is retired: palette transfer never modifies luma, so the post look owns tonality unconditionally.

Framing settled in the session: reference images = `Post(Palette(Art))`. Palette (per-texel hue identity, ramps, smoothing) is baked per-object; global grade (exposure, WB, contrast, saturation, curves, bloom, ACES) is per-scene and must never be baked into albedo. The reference images artists pick for the post look already have bloom and HSV baked in — that is correct for the post target, which is exactly why the post look (not the palette) should absorb those effects.

Out of scope: any change to the fit math itself (`NamerStylePostFit` moves home, not math), bloom-robust palette extraction (follow-up phase candidate), vibrance split (still deferred from 5.1), new runtime dependencies.

</domain>

<decisions>
## Implementation Decisions

### ToneMatch retirement (STYL-11)
- **D-01:** ToneMatch is **retired**, not hidden — profile field, profile inspector slider, `NamerStyleStylization.ToneMatch`, the `postOwnsTone` zeroing rule, the `_ToneMatch` kernel uniform path, and the tone-only `Active` OR-clause all go. Palette transfer becomes hue/vibrance-only (StyleStrength + HueReplaceMode) plus smoothing, byte-identically for those knobs. Anchor luma may still participate in nearest-anchor matching (identity), but is never transferred.
- **D-02:** Consequence to preserve: the zero-dispatch identity gate — an all-neutral profile must still compose the byte-identical null path with no extra leases/dispatches (the `Active` computation simplifies but the invariant stays).

### Standalone asset (STYL-10)
- **D-03:** The post look lives on a new `NamerPostLook` ScriptableObject. Fit Look, fitted-parameter display/hand-tweaking, and Volume generation move out of the embedded profile inspector in the Processor window into the asset's own custom Editor (main Inspector). Create via asset menu.
- **D-04:** Fit trigger = "Fit from current Processor render": the asset inspector's Fit action consumes the window's current forced-stylized exemplar render (the 05.1 plan-03 seam: forced-stylized recompute + readback + fit). The button is disabled with a status hint when the window has no stylized output. One render pipeline — the asset never renders its own exemplar.
- **D-05:** The asset owns its **own reference-image list**, decoupled from the style profile's palette references. Post references want final graded screenshots (bloom and all — that is the target); palette references stay on the profile. Weights/slots mirror the existing reference-slot UX.

### Per-scene Volumes (STYL-12)
- **D-06:** Each asset generates/refreshes its own URP Volume profile under the existing GEN-01/GEN-03 generated-asset conventions. Re-fit regenerates and overwrites the asset's generated Volume (asset is source of truth; hand-tweaks to a *generated* Volume are lost on re-fit). The per-scene workflow is **duplicate the asset, then tweak** — each duplicate is an independent look with its own generated Volume.

### Migration & preview
- **D-07:** 5.1-era fitted blocks (`Post*` fields, curves, fingerprint, exemplar name on `NamerStyleProfile`) migrate off the profile. Exact mechanics (load-time auto-migration creating an asset beside the profile vs. a one-time converter menu item vs. deprecate-and-ignore) are planner's discretion, but an existing fitted profile must not silently lose its look without a documented path.
- **D-08:** The "Stylized + Post" After View mode rewires to read a selected `NamerPostLook` asset (selection lands in the window UI); it no longer reads the profile's fitted block. Existing After View modes are unchanged. The 2D albedo preview stays lens-honest (no post simulation).

### Claude's Discretion
- Asset field layout and inspector structure (sections, buttons, status lines — the 05.1 P15–P20 inspector blocks are the donor pattern)
- Asset menu path and creation UX; whether the Processor window gains a "create/attach post look" affordance
- Migration mechanics under D-07; `FormerlySerializedAs` vs. clean delete on the profile
- Generated Volume naming/location relative to the asset (generated-assets directory conventions)
- What happens to the 05.1 Process-time companion-Volume regeneration seam (it follows the asset; exact call-site rewiring)
- Test fixture design for asset creation/fit/migration; which existing 5.1 tests move vs. get rewritten
- Kernel cleanup approach for `_ToneMatch` (full removal vs. permanently-zero uniform) — must respect the Metal unbound-property silent-skip rule: every constant a dispatched kernel references is set unconditionally

</decisions>

## Existing Code Insights

### Reusable Assets
- `NamerStylePostFit` — the whole deterministic fit (stats accumulate → Fit → params); consumes source stats from the stylized exemplar render and reference stats — unchanged, just re-homed
- 05.1 window exemplar seam — forced-stylized recompute + readback producing the source distribution; the asset's Fit action plugs in here (D-04)
- `NamerStyleVolumeWriter` — VolumeProfile assembly with named overrides + sub-asset wiring already exists
- `NamerStyleProfileEditor` P15–P20 — the fitted-parameter inspector blocks; donor markup for the asset's custom Editor

### Established Patterns
- Explicit action, never on debounce (Extract/Fit precedents) — the asset Fit action follows it
- Source of truth → generated assets derive and may be overwritten on regeneration (GEN-01/GEN-03) — asset → Volume follows it exactly
- Metal unbound-property silent-skip: every constant a dispatched kernel references is set unconditionally — applies to any kernel cleanup under D-01
- Zero-dispatch identity gate: null AND inactive stylization contexts must stay byte-identical with zero extra leases/dispatches (integration-test pinned)
- Editor asmdef already references URP Runtime/Core — Volume API reachable with no asmdef work

### Integration Points
- New `NamerPostLook : ScriptableObject` + its custom Editor (Editor/ or Editor/Stylize/)
- `NamerStyleProfile`: fitted-post block + ToneMatch removal; `Changed` event partial lives in the profile editor file (C# declaring-type-only constraint noted in STATE decisions)
- `NamerEditorWindow`: post-look asset selection for the Stylized + Post lens; Fit-action source-render exposure to the asset inspector
- `NamerProcessor`/Process path: companion-Volume regeneration call site rewires to the asset (or drops, per discretion)
- `NamerStyleStylization`/`NamerStylizePipeline`/`NAMERStylize.compute`: ToneMatch retirement

<specifics>
## Specific Ideas

User's model, verbatim (this session):
- "I'm thinking the extracting of style, should really only color palette match. and the fit look can be for the reference images for post processing.?"
- "The reason is that those reference images already have post-processing including bloom and probably some HSV applied."
- "Namer + stylized = color palette matching? / Namer + Stylized + Post = color palette matching + post processing that can be changed per scene."
- Decision 1 (ToneMatch): "retired"
- Decision 4 (asset view): "Yea, I think maybe this whole fit look, needs to get ripped out of the NAME panel and have it's own asset view that you can generate and tweak inside the main inspector?"

Design notes agreed in session:
- Fit-trigger coupling options were (a) fit-from-live-Processor-render [chosen], (b) baked source-stats snapshot for offline re-fit [deferred], (c) asset renders its own exemplar [rejected — duplicates the preview pipeline]
- Honest caveat carried forward: post-retirement, "Stylized" (no post) renders with original luma + matched hue/sat — expected to look flatter than the old ToneMatch=1 path; that is the model working as designed
- Bloom contamination of palette anchors (references have bloom baked in) is the acknowledged follow-up — NOT this phase

</specifics>

<deferred>
## Deferred Ideas

- **Bloom-robust palette extraction** — reject/downweight bloom-whitened highlights when building palette anchors (e.g. reuse the post fit's p95 Max3 bloom threshold as an extraction mask). Next phase candidate; explicitly out of scope here
- **Vibrance split control** (carried from 5.1) — post saturation + model-level vibrance baked into albedo; future phase
- **Source-stats snapshot on the asset** — bake histograms/sums at fit time so reference tweaks re-fit without a re-render (session option b); layer-on candidate after this phase
- **3D-LUT / ColorLookup route** — unchanged from 5.1: fallback only
- **2D albedo post simulation** — flat preview stays lens-honest

</deferred>
