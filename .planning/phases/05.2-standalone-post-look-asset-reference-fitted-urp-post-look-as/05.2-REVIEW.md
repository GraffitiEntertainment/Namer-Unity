## Warnings

### WR-01: Preflight-gate refusal escapes `RunFitLook` uncaught — the promised "Fit failed" HelpBox never renders

**File:** `Packages/com.graffitientertainment.namer/Editor/UI/NamerPostLookEditor.cs:431-432`
**Issue:** `NamerStyleVolumeWriter.PreflightWriteGate(look, settings)` executes inside the
outer `try` (line 386) which has **only a `finally`** (lines 450-454) — no `catch`. The
first inner `try/catch` (lines 395-403) wraps only `RunStylePostFit`; the second
(lines 440-448) wraps only the subsequent `Write` + `PingObject`. So when the preflight
gate throws `InvalidOperationException` — exactly the documented refusal cases: a foreign
(non-NamerGenerated) asset sitting at the composed path, or a destination escape — the
exception propagates out of `RunFitLook` into `OnInspectorGUI`, aborting the remainder of
that GUI pass with a console error. `fitError` stays null, so the locked
`"Fit failed: {message}"` HelpBox promised by the comment at lines 424-430 ("and 'Fit
failed' never reports after the fit itself was committed") and again at lines 438-439
("Any write-gate refusal surfaces here as the locked 'Fit failed: {message}' copy")
**never renders on any subsequent frame either**. The refusal path is reachable in normal
use (the writer's own test `Write_FromAsset_RefusesNonGeneratedOverwrite` exercises it),
and `RunRegenerateVolume` (lines 640-654) wraps the identical gate in a `try/catch`
("Volume regeneration failed: …") — the asymmetry confirms the omission. Note the
no-mutation-on-refusal property itself is intact (`Undo.RecordObject`/`ApplyToPostLook`
sit after the gate); the defect is purely the unhandled exception and the missing error
UI.
**Fix:** Wrap the preflight in its own catch that records `fitError` and returns — the
gate must stay before `Undo.RecordObject` to preserve CR-01 ordering:

```csharp
NamerProcessorSettings settings = new NamerProcessorSettings();
try
{
    NamerStyleVolumeWriter.PreflightWriteGate(look, settings);
}
catch (Exception exception)
{
    fitError = "Fit failed: " + exception.Message;
    return;
}
```

### WR-02: `CreateAndAttachPostLook` flushes every dirty asset in the project with `SaveAssets()`

**File:** `Packages/com.graffitientertainment.namer/Editor/UI/NamerEditorWindow.cs:2395-2397`
**Issue:** The new `CreateAndAttachPostLook` calls `AssetDatabase.SaveAssets()` right
after `AssetDatabase.CreateAsset(look, path)`. `CreateAsset` already persists the new
asset; the extra `SaveAssets()` force-writes **every other dirty asset in the project**
to disk — the exact anti-pattern this project's own WR-04 discipline forbids (see the
carried-over comment in `NamerStyleVolumeWriter.Write`, lines 145-149: "SaveAssets()
flushes every dirty asset in the project … never force-saves unrelated user work"). An
artist with unrelated in-progress asset edits gets them silently committed to disk as a
side effect of clicking "Create" in a save dialog. The donor `CreateAndAttachStyleProfile`
(line 2367) has the same flaw, but this phase introduced a fresh copy of it in new code.
**Fix:** Persist only the new asset:

```csharp
NamerPostLook look = ScriptableObject.CreateInstance<NamerPostLook>();
AssetDatabase.CreateAsset(look, path);
EditorUtility.SetDirty(look);
AssetDatabase.SaveAssetIfDirty(look);
```

(Or drop the flush entirely — `CreateAsset` writes the file; apply the same fix to the
donor at line 2367 in the same stroke.)

## Info

### IN-01: `Write` mutates the asset (`ClampToCaps`) before its own gate — a refusal no longer leaves the asset untouched for direct callers

**File:** `Packages/com.graffitientertainment.namer/Editor/Stylize/NamerStyleVolumeWriter.cs:89-91`
**Issue:** `Write` calls `look.ClampToCaps()` (line 89) **before**
`PreflightWriteGate(look, settings)` (line 91). For a direct `Write` caller (tests,
`RunRegenerateVolume` pre-gates first, so the editor flows are protected), a gate refusal
leaves the in-memory look object already sanitized/mutated — weakening the documented
"refusal leaves the asset untouched" contract (the gate's own doc comment, lines 44-53).
The mutation is not persisted (`SetDirty(look)` runs only after the gate), so the drift
is in-memory until domain reload, and `ClampToCaps` is idempotent — hence Info.
**Fix:** Swap lines 89 and 91 so the gate runs before `ClampToCaps` (the clamp then
still precedes every parameter read at lines 101-135).

### IN-02: `RunFitLook`'s `finally` raises `NamerPostLook.Changed` on no-op early returns

**File:** `Packages/com.graffitientertainment.namer/Editor/UI/NamerPostLookEditor.cs:450-454`
**Issue:** The `finally` unconditionally calls `NamerPostLook.RaiseChanged(look)`, so the
no-op paths — null exemplar window (line 389), user cancel (line 405), `NotExtracted`
(line 410), unreadable reference texture (line 417) — each fire the `Changed` event,
triggering a needless debounced preview recompute in every subscribed Processor window
even though nothing about the asset changed.
**Fix:** Track a `bool mutated` (set on the apply path), and raise in `finally` only when
it is true; the slider/curve edit paths already raise `Changed` themselves.

### IN-03: Static `_postCurveTexture` destroyed by any window instance's cleanup

**File:** `Packages/com.graffitientertainment.namer/Editor/UI/NamerEditorWindow.cs:374-380`
**Issue:** `_postCurveTexture`/`_postCurveTextureKey` are `static` (lines 166-167) but
destroyed/cleared in the per-instance cleanup (OnDisable path). With two Processor
windows open, closing one destroys the shared texture the surviving window may still
sample that frame (a transient missing-texture render). It self-heals on the next
`GetPostCurveTexture` call via the null check at line 884, so this is an edge-case
robustness note, not a live bug.
**Fix:** Only tear the shared cache down when the last instance closes (a static instance
counter), or accept the one-frame heal and note it at the field.
