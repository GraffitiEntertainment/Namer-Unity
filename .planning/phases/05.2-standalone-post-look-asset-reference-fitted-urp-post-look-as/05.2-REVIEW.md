## Critical Issues

### CR-01: Volume write stamps success (fingerprint + return) even when the VolumeProfile never persisted to disk

**File:** `Packages/com.graffitientertainment.namer/Editor/Stylize/NamerStyleVolumeWriter.cs:137-159`
**Issue:** `Write` never validates that `AssetDatabase.CreateAsset(volume, path)` (line 137) actually succeeded, and never checks `loaded` (line 151) for null before stamping. Neither gate on this path checks destination-folder existence: `AssetGenerator.ValidateComposedPath` (AssetGenerator.cs:381-392) only confines the path inside the destination, `AssetGenerator.EnsureWritableTarget` (775-797) only checks an existing target asset, and the only folder-ensure seam, `NamerProcessor.EnsureFolder` (NamerProcessor.cs:581), is private and used only on the material path (NamerProcessor.cs:85). Both `Write` callers (NamerPostLookEditor.cs:450 and :655) construct `new NamerProcessorSettings()`, whose `Destination` comes from EditorPrefs — a folder that legitimately may not exist (renamed/deleted folder, restored prefs on a new machine, destination never created by a Process run).

When the folder is missing, Unity's `CreateAsset` logs "Couldn't create asset file" but throws no C# exception. Execution then continues: `Stamp(null)` silently no-ops (AssetGenerator.cs:801-804), line 158 stamps `look.VolumeWriteFingerprint = look.ComputeParamsFingerprint()` anyway, line 159 dirties the look, and line 160 returns null. Downstream consequences, all wrong:

- `IsVolumeStale` reads false, so the A13 staleness warning is suppressed exactly when the Volume does not exist.
- In `RunFitLook` the fit was already committed to the asset (NamerPostLookEditor.cs:442-444), so the asset and its Volume desync with no HelpBox (no exception → `fitError` stays null); `EditorGUIUtility.PingObject(null)` is a silent no-op.
- The A11 status line (NamerPostLookEditor.cs:594-597) displays the composed Volume filename regardless of existence, reinforcing the false success.
- Retrying "Regenerate Volume" repeats the silent failure; only the console error hints at the cause.

The A13 doc comment at NamerStyleVolumeWriter.cs:154-155 promises the seam "starts honest" — on this path it starts false.

**Fix:**
```csharp
AssetDatabase.CreateAsset(volume, path);
// ... AddObjectToAsset block, SetDirty, SaveAssetIfDirty ...
VolumeProfile loaded = AssetDatabase.LoadAssetAtPath<VolumeProfile>(path);
if (loaded == null)
{
    throw new InvalidOperationException(
        "Failed to generate the post Volume at '" + path
        + "' — the destination folder does not exist. Create it (or run Process once) and retry.");
}
AssetGenerator.Stamp(loaded);
look.VolumeWriteFingerprint = look.ComputeParamsFingerprint();
```
Throwing before the fingerprint stamp routes the failure through the existing locked HelpBox copies in both callers ("Fit failed: …" at NamerPostLookEditor.cs:453-456, "Volume regeneration failed: …" at :658-661). Preferably also ensure the folder exists up front (expose an `EnsureFolder` seam or validate existence inside `PreflightWriteGate`, NamerStyleVolumeWriter.cs:54-59, so the refusal fires before the fit mutates the asset).

## Warnings

### WR-01: Fit Look preflight gate throw escapes as an uncaught editor exception instead of the locked "Fit failed" HelpBox

**File:** `Packages/com.graffitientertainment.namer/Editor/UI/NamerPostLookEditor.cs:440`
**Issue:** In `RunFitLook`, `NamerStyleVolumeWriter.PreflightWriteGate(look, settings)` sits between the two inner try/catch blocks: the first covers `RunStylePostFit` (lines 403-411), the second covers `Write` (lines 448-456), and the outer `try` (394) has only a `finally` (458-462) — no catch. The gate is documented to throw `InvalidOperationException` for a non-generated asset at the composed path or a destination escape (NamerStyleVolumeWriter.cs:54-69), so when a refusal fires the exception propagates out of `RunFitLook` into the GUI event path: the user gets an uncaught-exception console error, the fit silently never runs, and the A8 "Fit failed: {message}" HelpBox contract (documented at lines 446-447 and 279) is violated. `RunRegenerateVolume` (lines 651-661) wraps its identical gate + write in a single try/catch — the correct pattern — which confirms this placement is an oversight, not a choice.

Note the asset-safety property is unaffected (the gate runs before `Undo.RecordObject`/`ApplyToPostLook`, so a refusal still leaves the asset untouched); the defect is the error-surfacing path only.

**Fix:** Move line 440 inside the existing write try (the gate is idempotent and cheap):
```csharp
try
{
    NamerStyleVolumeWriter.PreflightWriteGate(look, settings);
    VolumeProfile volume = NamerStyleVolumeWriter.Write(look, settings);
    EditorGUIUtility.PingObject(volume);
}
catch (Exception exception)
{
    fitError = "Fit failed: " + exception.Message;
}
```
This keeps the pre-mutation ordering (gate before `Undo.RecordObject` on line 442 is only needed for the "refusal leaves asset untouched" property, which is preserved as long as the gate precedes line 442 — so if that ordering is retained, instead wrap lines 439-441 in their own try/catch assigning `fitError` and returning).

### WR-02: User guide claims the window tracks the Editor selection — the shipped behavior is an explicit pick that deliberately does not

**File:** `docs/USER_GUIDE.md:15`
**Issue:** "The window tracks the current Editor selection automatically, so whatever you select appears in the Source section and the preview." The code states the opposite, verbatim, in the Source tooltip (NamerEditorWindow.cs:1466-1473): "This pick is explicit — it does NOT follow the editor selection; clicking other items or empty space leaves it unchanged." The persistent-pick behavior is also pinned by `NamerEditorWindowSmokeTests` (persistent Source pick). A user following the guide will click objects in the scene and conclude the tool is broken when the Source does not change. This is the guide's opening description of the primary input workflow, so the contradiction is user-facing, not cosmetic.

**Fix:** Replace the sentence with behavior-matching copy, e.g.: "The Source is an explicit pick: assign a GameObject, prefab, model, material, or folder in the Processor window's Source field. The pick is persistent — it does not follow the current Editor selection, so clicking other items or empty space leaves it unchanged."

### IN-02: ClampToCaps sanitize mutations land outside the Undo transaction, so Ctrl+Z cannot restore the pre-clamp values

**File:** `Packages/com.graffitientertainment.namer/Editor/UI/NamerEditorWindow.cs:2765` (with `Packages/com.graffitientertainment.namer/Editor/UI/NamerPostLookEditor.cs:442`)
**Issue:** `RunStylePostFit` calls `look.ClampToCaps()` at window line 2765, but the only `Undo.RecordObject(look, "Fit Look")` happens later, at NamerPostLookEditor.cs:442 — after `RunStylePostFit` returns (called at :405). Any values `ClampToCaps` changes (hand-edited out-of-range fields, NaN curve resets) are mutated before the snapshot, so undo after a fit restores the already-clamped state, never what the user last saw. In the Regenerate Volume path the writer's own `look.ClampToCaps()` (NamerStyleVolumeWriter.cs:89) runs with no Undo record at all. Impact is bounded — `ClampToCaps` only rewrites invalid/out-of-cap values — which is why this is Info, not Warning.

**Fix:** Record before sanitizing: in `RunFitLook`, hoist `Undo.RecordObject(look, "Fit Look")` to before the `RunStylePostFit` call (a no-op snapshot when nothing changed), or have `RunStylePostFit` leave the asset untouched and perform the sanitize after the record.

### IN-03: Fingerprint/ClampToCaps logic near-duplicated between NamerPostLook and NamerStyleProfile

**File:** `Packages/com.graffitientertainment.namer/Editor/Stylize/NamerPostLook.cs:156, 225` and `Packages/com.graffitientertainment.namer/Editor/Stylize/NamerStyleProfile.cs:180, 214`
**Issue:** `ComputeFingerprint` and `ClampToCaps` exist as parallel near-identical implementations (GUID:weight identity pipe-strings; NaN-then-clamp with curve resets). The 05.2 re-home makes this deliberate (the post look is the profile's palette-side twin), but the two copies must stay behaviorally aligned by hand — a future cap change on one side (e.g. a `NamerEditorConstants` limit consumed by only one `ClampToCaps`) silently diverges the staleness seams. Noted as a drift risk, not a defect; no refactor requested under the minimal-change rule.

**Fix:** Leave as-is, but add a cross-reference comment on each `ClampToCaps`/`ComputeFingerprint` naming its twin ("keep aligned with NamerPostLook.ClampToCaps / NamerStyleProfile.ClampToCaps") so future edits grep for both.
