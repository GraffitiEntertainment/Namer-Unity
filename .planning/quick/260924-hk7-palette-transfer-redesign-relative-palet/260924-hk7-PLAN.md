<objective>
Redesign CSPaletteTransfer from an absolute-snap operator to a relative palette ramp with an independent Tone Match option (user-approved design, quick 260924-hk7). Fixes two user-reported defects: (1) the kernel lerps texel luma toward the matched anchor's ABSOLUTE luma via _StyleStrength, so dark-browns flatten to the anchor's light brown; (2) with this project's real extracted anchors (all sat >= 0.20 because k-means centroids drifted above the 0.15 achromatic cutoff), achromatic texels fall into the chromatic fallback and get lifted/tinted — black eyes turn gray.

Purpose: restore source tonality by default while keeping hue-family styling and vibrance, with luma pull as an explicit opt-in.
Output: redesigned kernel + ToneMatch profile control end-to-end + re-specced test suite (tests ARE the specification — coverage is not weakened, it is re-pinned to the new operator).
</objective>

<approved_design>
User-approved redesign (option: "Yes — but keep a tone-match option"). Record and implement exactly:

1. Hue: UNCHANGED — circular ramp toward the matched anchor's hue family; Preserve (f = strength) /
   Replace (f = 1) modes stay. Hue is only ever ramped for CHROMATIC texels (as today).
2. Saturation: boost-only pull for CHROMATIC texels only:
   outSat = max(srcSat, lerp(srcSat, anchorSat, strength)). Never desaturates; chromatic texels
   matched to achromatic-flagged anchors self-guard via max(). ACHROMATIC texels
   (sat < NAMER_STYLIZE_ACHROMATIC_CUTOFF) keep srcSat untouched — blacks/grays can never be tinted.
3. Luma: source luma preserved by default — the absolute luma pull moves OUT of the _StyleStrength
   path into a NEW _ToneMatch uniform:
   outLuma = lerp(srcLuma, anchorLuma, saturate(_ToneMatch)) for ALL texels. Achromatic texels
   still match achromatic anchors by luma distance; hue untouched for them (as today).
4. New profile control: serialized float ToneMatch [0,1], default 0
   (NamerEditorConstants.DefaultToneMatch = 0f), clamped in NamerStyleProfile.ClampToCaps, wired
   through NamerStyleStylization (new field + Create() reads profile.ToneMatch), slider in
   NamerStyleProfileEditor.DrawParameterSliders placed right after the Style Strength slider,
   tooltip stating: 0 preserves the source's own tonality; higher values pull brightness toward
   the reference anchors' luma.
5. Active gate: NamerStyleStylization.Active also ORs (PaletteAvailable && ToneMatch > 0) so
   tone-only contexts dispatch.
6. Uniform discipline: _ToneMatch is set UNCONDITIONALLY in NamerStylizePipeline.Run next to
   _StyleStrength/_HueReplaceMode/_AnchorCount (documented project pitfall — Metal skips dispatches
   on unbound kernel properties; the Stage 3 comment block names this).

Semantics amendment (record in test comments): StyleStrength 1.0 now means full hue-family shift +
full vibrance boost; tonality is controlled independently by Tone Match. Old profile assets
deserialize ToneMatch = 0 -> the new safe default automatically.

Trade-off acknowledged by the user: a pastel (less saturated than source) reference cannot soften
a vivid source — boost-only.

Out of scope (do NOT touch): docs/USER_GUIDE.md, NamerProcessor.StylizationNeedsMesh (smoothing-only
concern), extractor/anchor pipeline, bilateral kernels, NamerEditorWindow (inherits the slider via
the embedded profile inspector).
</approved_design>
